# Step 2.8b：handler 接上 service

## 目標與結果
把 501 stub 換成真正的 `CreateAccount` handler，並在 `main.go` 手動接線：`db → repo → service → handler`。
`POST /api/accounts` 現在會回 201、409、422，其他錯誤回 500。
`make test` 通過，後端覆蓋率 90.9%（門檻 80%）。
手動驗收：三個 curl 的狀態碼正確；DB 的 `password_hash` 欄位是 `$2a$10$` 開頭的 bcrypt hash；每行 log 都是 JSON 且帶 `request_id`。

## 學到的概念

**Handler 是 HTTP 翻譯員**：只負責取出請求資料、呼叫 service、把結果翻成 status code。
Spring 的 `@ControllerAdvice` + `@ExceptionHandler` 對應到 Go 的 `errors.As` / `errors.Is`。
Go 的錯誤是回傳值，不會自動往上拋，所以每個 handler 要自己判斷。

```go
var verr *ValidationError
switch {
case errors.As(err, &verr):          // 422
case errors.Is(err, ErrEmployeeIDTaken): // 409
default:                              // 500
}
```

**strict server 的慣例**：業務錯誤要放在 response 裡回傳，`error` 回 `nil`。
`error` 不是 `nil` 時，生成的包裝函式不會呼叫 `Visit...`，而是走通用錯誤處理，回應就不是 spec 定義的 Error JSON。

**手動接線**：Spring 靠 `@Autowired` 和容器自動組裝，Go 在 `main.go` 照依賴順序自己建。多寫的幾行是刻意的明確性。

```go
repo := account.NewRepository(db)
svc := account.NewService(repo)
accountHandler := account.NewHandler(svc, logger)
```

**500 不洩漏內部細節**：完整原因只寫進 log，回給 client 的 message 是固定字串。

**log 的 request-id 由 `ContextHandler` 自動加**：用 `ErrorContext(ctx, ...)` 傳入 ctx 就會帶上。手動再加一次會讓同一行有兩個 `request_id`。
回應 body 的 `requestId` 欄位是 API 的一部分，要手動填。

**slog 的 key-value 是靠位置配對**：少一個 key 或多一個 key，編譯器不會報錯，要靠 `go vet`。`go test` 會自動跑部分 vet 檢查，所以這次在測試時被擋下。

**測試分層**：handler 測試用「真的 service + 假的 repo」，只替換 DB，仍驗證到真正的錯誤對應。
`go build` 不編譯 `_test.go`，測試檔的問題要到 `go test` 才會出現。

## 提問與除錯
- 學習者指出 DB 欄位名是 `password_hash`，不是 `password`。導師給的查詢語句寫錯，已更正。
- 導師給的 `handler.go` 在 log 裡多手動加了 `request_id`，會與 `ContextHandler` 重複。刪除時漏刪了一半，留下 `"request_id", "error", err`，`go vet` 回報 `arg "err" should be a string or a slog.Attr`。補刪後通過。
- 問：為什麼 API 前綴是 `/api` 不是 `/api/v1`？
  答：PRD 沒有寫理由。版本前綴解決的是「有無法控制的外部 client，API 需要破壞性變更」的問題。
  這個專案前後端同 repo、同源、一起部署，沒有這個需求。日後要開放給外部系統時再加，成本不高。決定：維持 `/api`。

## 自我檢查
1. handler 若改成 `return nil, ErrEmployeeIDTaken` 會怎樣？
   答：生成的包裝函式不呼叫 `Visit`，走通用錯誤處理，回應不是 spec 定義的 Error JSON。
   學習者曾誤選「回 409，沒有差別」：strict server 不會自己依錯誤種類對應 status code，對應是 handler 的工作。
2. 500 為什麼只把 `err` 寫進 log，回給 client 固定的 "internal error"？
   答：避免洩漏內部細節（SQL、主機名等），完整原因留給維運人員在 log 查。

# 3.5a 登入 handler 與 Cookie

## 目標與結果

`POST /api/sessions` 現在是真的實作：帳密正確回 201，body 是 Account，header 帶
`Set-Cookie: session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax`；帳密錯回 401；欄位為空回 422；其他錯誤回 500。
`curl -i` 手動驗證四種情況都符合。

登出（`DELETE /api/sessions/current`）拆到 3.5b，排在 3.6 的認證 middleware 之後，
因為 strict handler 的 request 物件沒有 Cookie，登出需要 middleware 把 token 放進 context。

檔案：

- `backend/internal/auth/service.go`：`Login` 改回 `(token, *account.Account, error)`
- `backend/internal/auth/handler.go`：`CreateSession`、`sessionCookie`
- `backend/cmd/api/main.go`：手動接線 `session.Repository` → `auth.Service` → `SessionHandler`
- `backend/internal/auth/handler_test.go`：fake service，測 201 / 401 / 422 / 500

## 學到的概念

### Set-Cookie 與屬性

| 屬性 | 作用 |
|---|---|
| `HttpOnly` | JavaScript 讀不到，XSS 偷不到 token |
| `Secure` | 只走 HTTPS |
| `SameSite=Lax` | 跨站 POST 不帶 Cookie，擋一部分 CSRF（不夠，3.7 還要 CSRF token） |
| `Path=/` | 整個網站都帶 |
| 不設 `Max-Age` | 瀏覽器關閉後丟掉；有效期限以資料庫為準（閒置 30 分鐘、絕對 8 小時） |

前後端同源，Cookie 自動帶，不需要 CORS。

```go
c := http.Cookie{Name: "session", Value: token, Path: "/", HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode}
header := c.String()
```

Spring 類比：`ResponseCookie`。`HttpSession` 的 `JSESSIONID` 是容器自動發的，Go 要自己組。

### 消費者定義 interface

`loginService` 定義在 handler 這一側（使用端），`*auth.Service` 不用寫 `implements`，方法簽名對上就自動滿足。
測試傳 `fakeLogin`，不需要 Mockito。缺方法時，編譯錯誤出現在「使用處」（`main.go`），不是出現在缺方法的檔案。

### 手動接線

Spring 用 `@Autowired` 與 component scan；Go 在 `newHandler` 一層層 `New…` 並傳入，被依賴者要先建。
多寫的程式碼是刻意的明確性。

### 其他

- 多回傳值：回 `(string, *account.Account, error)`，失敗時其他值不可用（慣例回 `nil`）。
- 驗證順序：空欄位在查 DB 之前就回 422，避免空密碼觸發昂貴的 bcrypt。
- 失敗統一訊息：帳號不存在與密碼錯都回同一個 401（搭配 3.4b 的 `dummyHash`），避免枚舉工號。
- 500 只記 log，不把原因回給客戶端。

## 問題與解答

**Q：`go build` 說 `server` 沒實作 `StrictServerInterface (missing method DeleteCurrentSession)`？**
A：貼 diff 時把 `DeleteCurrentSession`、`GetCurrentAccount` 兩個 501 stub 也刪掉了。補回即可。

**Q：`TestStubsReturn501` panic（nil pointer）？**
A：舊測試斷言 `CreateSession` 是 501 stub，並傳空的 request（`Body == nil`）。實作後測試過時，改測真實行為。

## 自我檢查

1. 拿掉 `HttpOnly: true` 會怎樣？答：頁面上的 JavaScript 可以讀到 token（XSS 可偷 session）。
2. 帳號不存在與密碼錯誤都回同一個 401，為了什麼？答：避免攻擊者藉由回應差異列舉有效工號。

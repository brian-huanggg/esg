# Step 2.7：account service：驗證與 bcrypt

## 目標與結果
`Service.Register(ctx, employeeID, name, password)` 先驗證輸入，無效時回傳 `*ValidationError`（附欄位錯誤清單），不呼叫 repository。
有效時用 bcrypt cost 10 雜湊密碼，存進去的字串以 `$2a$10$` 開頭，再交給 repository。
`make test` 通過，後端覆蓋率 90.2%（門檻 80%）。對應 PRD「密碼只存 Hash」與錯誤順序第 7 項（422）。

## 學到的概念

**為什麼用 bcrypt 而不是 SHA-256**：SHA-256 為「快」設計，GPU 每秒可試數十億組。bcrypt 刻意很慢，而且每次自帶隨機 salt。
**cost 10**：代表 2¹⁰ 輪，每加 1 成本翻倍。這是專案不變量。
**72 byte 上限**：bcrypt 只看前 72 bytes，所以超過就拒絕，不要默默截斷。是 byte 不是字元，中文一字 3 bytes。
```go
if len(password) < minPasswordLen || len(password) > maxPasswordLen { ... } // len = bytes
utf8.RuneCountInString(name) > maxNameLen                                    // 字元數，對齊 VARCHAR(100)
```

**service 與 handler 的分工**：handler 管 HTTP（解析、status code），service 管業務規則（驗證、雜湊）。service 不知道 HTTP 存在。
Spring 對應 `@Service`。

**手動接線**：`NewService(repo)` 由 `main.go` 手動傳入依賴（Step 2.8），沒有 `@Autowired`。
錯誤也是手動：回傳 `*ValidationError`，呼叫端用 `errors.As` 判斷，沒有 `@Valid` 加 exception。

**interface 定義在使用端**：service 只需要「能 Create 的東西」，所以在 service.go 宣告小 interface `accountCreator`。
測試手寫 `fakeRepo` 滿足它，Go 沒有 Mockito。
```go
type accountCreator interface {
    Create(ctx context.Context, a *Account) error
}
```

**錯誤原樣往上傳**：repository 的 `ErrEmployeeIDTaken` 不改寫，handler 之後用 `errors.Is` 判斷即可。

## 提問與除錯
- 第一次跑測試 6 個失敗：`regexp.MustCompile(`$[0-9]{6}$`)` 把 `^` 寫成 `$`。
  `$` 代表字串結尾，所以任何輸入都比對不到，連有效工號也被拒絕。
  線索：只有「本來就該報 employeeId 錯」的 2 個測試通過。修成 `^[0-9]{6}$`。

## 自我檢查
1. 把 `len(password)` 改成 `utf8.RuneCountInString(password)` 會怎樣？
   答：超過 72 bytes 的密碼可能通過驗證。例如 30 個中文字元算 30，實際 90 bytes，bcrypt 會忽略第 72 byte 之後的內容。
2. 先驗證再 `TrimSpace`，輸入 `"   "` 會怎樣？
   答：原始字串長度 3、不是空字串，所以通過驗證，之後 trim 變成空字串寫進 DB。所以要先 trim 再驗證。

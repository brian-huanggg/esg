# 3.3 session repository

## 目標與結果

新增 `backend/internal/session/repository.go`，提供四個方法：`Create`、`FindActive`、`Touch`、`Delete`。
整合測試涵蓋有效、閒置逾時、絕對逾時、已刪除，另有一個 `Touch` 測試。

檔案：

- `backend/internal/session/repository.go`
- `backend/internal/session/repository_test.go`

## 學到的概念

### 單一 SQL 同時判斷

閒置 30 分鐘和絕對 8 小時的條件都寫在 `WHERE`，由資料庫的時鐘（`UTC_TIMESTAMP(3)`）判斷。
應用程式不先查整列再比時間，也不使用 `time.Now()`。

```sql
SELECT account_id FROM sessions
WHERE token_hash = ?
  AND last_seen_at > UTC_TIMESTAMP(3) - INTERVAL ? MINUTE
  AND expires_at   > UTC_TIMESTAMP(3)
```

`Touch` 的 `UPDATE` 使用相同的 `WHERE`，過期的 session 不會被續命。
MariaDB 的 `UPDATE` 沒有 `RETURNING`，所以查詢和更新各寫一次。

### 錯誤處理

- 未知、閒置逾時、絕對逾時一律回 `ErrNotFound`，呼叫端無法區分（沒權限一律當作不存在）。
- `Delete` 不檢查 `RowsAffected`，重複登出不是錯誤。
- Go 沒有 exception，用 sentinel error 加 `errors.Is`；其他錯誤用 `%w` 包裝保留原因。

### 測試：用 SQL 倒撥時間

不 sleep、不用 `time.Now()`，用 `UPDATE ... SET col = UTC_TIMESTAMP(3) - INTERVAL ? MINUTE` 倒撥，
讓測試和被測的判斷使用同一個資料庫時鐘。

### Spring 對照

Spring Session JDBC 的 `JdbcIndexedSessionRepository`。Go 要在 `main.go` 手動接線
（`NewRepository(db)`），沒有 `@Repository` 加 `@Autowired`；這在 3.5 才接。

## 問題與解答

- 編譯錯誤 `fresh redeclared in this block`：同一個 block 內變數宣告了兩次，刪掉重複的一行。

## 自我檢查

1. 拿掉 FindActive 的 `expires_at > UTC_TIMESTAMP(3)`，哪個測試失敗？
   答：`TestFindActive_AbsoluteTimeout`。它的 `last_seen_at` 是新鮮的，只靠 `expires_at` 條件擋下。
   `Valid` 的 `expires_at` 在未來，有沒有條件都通過；`Deleted` 整列已刪除，與條件無關；
   `IdleTimeout` 由 `last_seen_at` 條件擋下。
2. 為什麼逾時測試用 SQL 倒撥 `last_seen_at`？
   答：sleep 30 分鐘太慢，而且判斷逾時的是資料庫時鐘，測試要操作同一個時鐘。

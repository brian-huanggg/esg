# 1.9 前端測試與覆蓋率門檻

> tag：`step-01-09`
> 檔案：`frontend/src/App.test.tsx`、`frontend/vite.config.ts`、`frontend/package.json`、`Makefile`
> 對應：PRD「後端測試覆蓋率 >= 80%」；測試 3.4「在 CI 強制覆蓋率門檻」

## 目標與結果

`make test` 一次跑完前後端測試，後端覆蓋率（排除 generated code 和 `main.go`）低於 80% 時失敗。

- 全部測試都在：後端 `90.9%`，前端 `2 passed`，`exit code: 0`
- 移走 `logging_test.go`：後端 `45.5%` → `FAIL: backend coverage below threshold`，`exit code: 2`，
  前端測試不會跑（make 遇到失敗就停）
- `make test COVER_MIN=100` 可以從指令列覆寫門檻

## Pseudocode

```
make test
 ├─ test-backend
 │    go test -coverprofile → coverage.out（每一段程式有沒有被跑到）
 │    sed 刪掉 *.gen.go 和 cmd/api/main.go 的列
 │    go tool cover -func 算出 total → awk 跟 COVER_MIN 比，低於就 exit 1
 └─ test-frontend
      vitest run（jsdom 環境）跑 *.test.tsx
```

## 學到的概念

### 1. Vitest：前端的 `go test`

| | Go | 前端 |
|---|---|---|
| 測試檔 | `xxx_test.go` | `Xxx.test.tsx` |
| 一個測試 | `t.Run(name, func...)` | `it(name, () => {...})` |
| 斷言 | `if got != want { t.Errorf }` | `expect(got).toBe(want)` |

- `"test": "vitest run"`：一定要加 `run`。只寫 `vitest` 會進 watch 模式，跑完不會結束，make 和 CI 會卡住
- Vitest 跟 Vite 共用 `vite.config.ts`，`test` 欄位要放在**最外層**，和 `server` 同一層
- 要加 `/// <reference types="vitest/config" />`，不然 `tsc` 不認得 `test` 欄位
- Node 沒有 DOM，`test.environment: 'jsdom'` 提供模擬的 `document`

### 2. Testing Library：用使用者的角度測

只問「畫面上看得到什麼」，不檢查 component 的內部狀態：

```tsx
render(<App />)
expect(await screen.findByText('Backend: ok')).toBeTruthy()
```

| 想斷言的事 | 用哪個 |
|---|---|
| 現在畫面上**有** | `getBy...`（找不到直接 throw） |
| 現在畫面上**沒有** | `queryBy...`（找不到回傳 `null`） |
| **等一下**才會出現 | `await findBy...`（重試到逾時） |

- 沒開 vitest 的 globals，Testing Library 無法自動清理，所以要自己寫 `afterEach(() => { cleanup() })`

### 3. Mock fetch

```ts
vi.stubGlobal('fetch', vi.fn().mockResolvedValue(new Response('{"status":"ok"}', { status: 200 })))
// afterEach: vi.unstubAllGlobals()
```

用 Node 內建的 `Response`，`client.ts` 的 `res.ok` / `res.json()` 會照真的流程跑。概念跟 Go 的 `httptest` 一樣：
把外部依賴換成能控制的假東西。

### 4. 覆蓋率門檻怎麼算

- `coverage.out` 每一列是「檔案:位置 statement 數 有沒有跑到」，可以用 `sed '/pattern/d'` 過濾
- 排除 `*.gen.go`：不是我們寫的，算進去會灌大分母
- 排除 `cmd/api/main.go`：`main` / `run` 呼叫 `ListenAndServe`、`os.Exit`，單元測試測不到。
  只排除 generated code 時是 72.7%，連 main.go 一起排除後是 90.9%。代價是邏輯不能寫進 `main.go`
- Makefile 裡的 `$` 要寫成 `$$`；`?=` 讓指令列的值優先

### 5. Makefile 的兩個坑

- 規則底下的指令必須用 **Tab** 開頭，不然會出現 `missing separator`。用 `cat -A` 看：`^I` 是 Tab
- 指令行的 `#` 註解會被 make 印出來（交給 shell 跳過）；放在規則外、不加 Tab 才是 make 的註解

## 這一步踩到的坑：假的綠燈

這一步出現了兩次「測試通過，但其實什麼都沒驗證」：

1. **Makefile 漏了上下文行**：`test-backend` 只剩 `sed`，`go test` 和門檻檢查都不見了。
   `sed` 改的是上一次留下的 `coverage.out`，所以沒報錯。
   教訓：diff 裡沒有 `+` / `-` 的行是上下文，要保留
2. **`render(<App />)` 寫成 `return (<App/>)`**：測試函式直接 return，後面的 `expect` 都沒執行到，
   這個測試永遠會通過。`tsc` 只會把「unreachable code」當成提示，不會報錯。
   教訓：寫完測試後，故意把預期值改錯（例如改成 `'Backend: banana'`），確認測試**會失敗**

## 學習者的問題

- **Q：`cd frontend && npm run build && cd ..` 為什麼後面的指令都失敗？**
  `&&` 只在前一個成功時才執行下一個。build 失敗 → `cd ..` 沒跑 → 還停在 `frontend/`。
  另外，Claude Code 的 `!` 指令每次都從 repo 根目錄開始，不需要 `cd ..`

## 自我檢查

**Q1.** 把 `await screen.findByText('Backend: ok')` 改成 `screen.getByText('Backend: ok')`，會怎樣？
**A.** 失敗。render 完畫面還是 `loading...`，`fetch` 是非同步的；`getByText` 馬上找，找不到就直接 throw。

**Q2.** `main_test.go` 經過 `newHandler` 也會執行 `logging.go`，為什麼拿掉 `logging_test.go` 後，
`middleware` 的覆蓋率還是掉到 42.9%？
**A.** 覆蓋率是**每個套件**分開算的。`go test ./...` 為每個套件分別編譯測試程式，預設只記錄正在被測的那個套件。
`main_test.go` 屬於 `cmd/api`，它走進 `middleware` 的程式碼不會被記錄。
`-coverpkg=./...` 可以跨套件計算，但我們刻意不用：每個套件應該由自己的測試負責，不然門檻就擋不住漏測。

# 3.4b auth service

## 目標與結果

新增 `auth.Service.Login(ctx, employeeID, password)`：驗證帳密，成功時產生隨機 token、把 SHA-256 雜湊存進 `sessions`，
回傳明文 token（3.5 會把它放進 Cookie）。失敗一律回 `ErrInvalidCredentials`。
用手寫 fake 做單元測試，不碰資料庫。

檔案：

- `backend/internal/auth/service.go`
- `backend/internal/auth/service_test.go`

`main.go` 這步沒有接線，留到 3.5。

## 學到的概念

### `crypto/rand` 與 `math/rand`

`math/rand` 是可預測的偽隨機；`crypto/rand` 讀作業系統的安全隨機源。Session token 要讓攻擊者猜不到，所以用 `crypto/rand`。
Spring 類比：`SecureRandom` 對應 `crypto/rand`，`java.util.Random` 對應 `math/rand`。

```go
raw := make([]byte, 32) // 256 bits
_, err := rand.Read(raw)
token := base64.RawURLEncoding.EncodeToString(raw) // cookie-safe characters
```

### 只存雜湊

資料庫只存 `sha256.Sum256([]byte(token))`。資料庫外洩時，攻擊者拿不到 Cookie 裡的 token，不能冒用 session。
token 是 256 位元隨機值，不像密碼需要慢雜湊，所以用 SHA-256 而不是 bcrypt。
雜湊的是編碼後的字串，3.6 的 middleware 對 Cookie 值直接 `sha256.Sum256` 即可，不用先解碼。

### 防帳號枚舉

帳號不存在時改比對 `dummyHash`，讓這條路徑也花一次 bcrypt 的時間，攻擊者無法由回應時間判斷工號是否存在。
錯誤訊息也統一為 `ErrInvalidCredentials`。

```go
hash := dummyHash
acc, err := s.accounts.FindByEmployeeID(ctx, employeeID)
// ErrNotFound: keep dummyHash; other errors: return as is
cmpErr := bcrypt.CompareHashAndPassword(hash, []byte(password))
if acc == nil || cmpErr != nil {
	return "", ErrInvalidCredentials
}
```

`acc == nil` 的檢查確保即使有人用 `"dummy-password"` 也不可能登入。
`dummyHash` 在套件載入時用 `bcrypt.GenerateFromPassword`（cost 10，跟註冊一致）算一次。

### DB 錯誤不能偽裝

`FindByEmployeeID` 回 `ErrNotFound` 以外的錯誤時，原樣包裝回傳，不轉成 `ErrInvalidCredentials`，
否則資料庫故障會看起來像密碼錯誤。

### Go 要手動接線的地方

- `NewService(accounts, sessions)`：依賴靠建構子傳入，Spring 由 DI 容器 `@Autowired`。
- 使用方定義小 interface（`accountFinder`、`sessionCreator`），repo 不用宣告實作。
- 手寫 `fakeAccounts`、`fakeSessions`，沒有 Mockito。
- 逐步檢查 `error`，沒有 exception 往上拋。

這些多寫的程式碼是刻意的明確性，不是遺漏。

## 問題與解答

- Q：`acc` 和 `boom` 是什麼？
  A：`acc` 是 `account` 的縮寫（`account` 是套件名，同名會蓋掉套件）；查不到時為 `nil`。
  `boom` 是測試裡捏造的假錯誤 `errors.New("db down")`，用來驗證 DB 錯誤被原樣往上傳。
- 觀察：測試中 `unknown_employee` 花 0.06s、`wrong_password` 花 0.00s，因為測試帳號用 `bcrypt.MinCost`，
  `dummyHash` 用 cost 10。這是測試的人為差異，正式環境兩邊都是 cost 10。

## 自我檢查

1. 帳號不存在時直接回 `ErrInvalidCredentials`，不跑 dummy bcrypt，會怎樣？
   答：回應時間洩漏帳號是否存在（不存在立刻回應，存在則要等 bcrypt）。
2. 為什麼只存 token 的 SHA-256？
   答：資料庫外洩時攻擊者無法反推 token，不能拿來登入。（不是查詢速度，也不是省空間；第一次答「查詢較快」，補充後答對）

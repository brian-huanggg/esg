# 5.1 Migration：proposals 資料表

## 目標與結果

建立 `proposals` 資料表，作為 M5 提案 CRUD 的基礎。

- 新增 `backend/migrations/000004_create_proposals.up.sql` / `.down.sql`
- `make migrate-up` → `4/u create_proposals`
- `make migrate-down` → `4/d create_proposals`，再 up 一次也成功，代表 down 確實是 up 的反操作
- `make test` 通過，後端覆蓋率 90.7%

## 學到的概念

### 1. 雙 ID

寫法跟 `accounts` 一樣：`id BIGINT` 是內部主鍵，給 FK 和 JOIN 用；`uuid UUID` 是對外 ID，放在 URL 的 `{id}`。

FK 欄位 `leader_account_id` 的型別必須和 `accounts.id` 完全一樣（`BIGINT UNSIGNED`）。型別不同時，InnoDB 會拒絕建立 FK（`errno: 150`）。

### 2. 複合唯一鍵（composite UNIQUE）

```sql
UNIQUE KEY uq_proposals_leader_title (leader_account_id, title)
```

DB 檢查的是「兩個欄位的組合」有沒有重複，單獨一欄重複沒關係：

| leader_account_id | title | 結果 |
|---|---|---|
| 1 | 太陽能 | OK |
| 2 | 太陽能 | OK（不同 Leader） |
| 1 | 太陽能 | 1062 Duplicate entry |

- 對應 PRD 2.3「同一位 Leader 的提案名稱不可以重複」
- Spring 類比：`@Table(uniqueConstraints = @UniqueConstraint(columnNames = {...}))`
- 為什麼不在 Go 裡先 `SELECT` 檢查？兩個請求可能同時通過檢查，然後一起 INSERT（race condition）。DB 約束是原子的
- 最左前綴：這個索引也能拿來查 `WHERE leader_account_id = ?`，所以 5.6 的列表查詢不用再另外建索引

### 3. version 與樂觀鎖

要解決的是遺失更新（lost update）：兩個人讀到同一個版本，後寫的人會蓋掉先寫的人。

```sql
UPDATE proposals
SET title = ?, description = ?, version = version + 1, updated_at = UTC_TIMESTAMP(3)
WHERE uuid = ? AND leader_account_id = ? AND version = ?
```

- 影響 0 列 → 版本已經被別人改過 → 412
- 請求沒有帶 `If-Match` → 428
- `GET` 時回傳 `ETag: "3"`，`PUT` 時要帶 `If-Match: "3"`
- 為什麼用整數，不用 `updated_at`：兩次寫入可能落在同一毫秒，整數遞增最單純
- 為什麼用樂觀鎖，不用 `SELECT … FOR UPDATE`：使用者在瀏覽器上可能編輯好幾分鐘，不能一直鎖著那一列
- Spring 類比：JPA `@Version`。Hibernate 會自動加 WHERE 條件、自動加 1、丟出 `OptimisticLockException`；Go 這三件事都要自己寫

### 4. ON DELETE RESTRICT

某個帳號底下還有提案時，刪除這個帳號會被 DB 拒絕：

```
Error 1451: Cannot delete or update a parent row: a foreign key constraint fails
```

- `sessions` 用 CASCADE：session 本來就是暫時的，跟著帳號一起刪掉沒關係
- `proposals` 用 RESTRICT：提案是業務資料，不能因為刪帳號就跟著消失。M7 之後提案還有 MinIO 檔案，DB cascade 刪不到那些檔案
- 現在 PRD 沒有「刪除帳號」功能，RESTRICT 只是一道保險
- 將來如果要做刪帳號：在交易裡先處理提案、把 1451 轉成 409，或改用軟刪除（`disabled_at`）

### 5. 時間欄位

`updated_at` 沒有寫 `ON UPDATE`，因為 MariaDB 的 `ON UPDATE` 只接受 `CURRENT_TIMESTAMP`，而它用的是 session 時區，不保證是 UTC。所以之後的 UPDATE 語句要自己寫 `updated_at = UTC_TIMESTAMP(3)`。

## 觀察到的現象

- `SHOW CREATE TABLE` 輸出的 FK 後面沒有 `ON DELETE RESTRICT`，因為 RESTRICT 是預設值，MariaDB 只會印出跟預設不同的選項。migration 裡明寫，是為了讓讀程式碼的人知道這是刻意的選擇
- collation 是 `utf8mb4_uca1400_ai_ci`（MariaDB 11.4 的預設），不分大小寫（ci），也不分重音（ai）。所以 `Solar` / `solar`、`café` / `cafe` 都會被唯一鍵當成重複
- `bigint(20)` 括號裡的數字只是顯示寬度，不會限制數值範圍
- `\G` 本身就是結束符號，後面再加 `;` 會多跑一次空查詢，出現 `No query specified`

## 學習者的問題

**Q：什麼叫做 composite UNIQUE？**
A：見上面第 2 節。唯一性看的是「欄位組合」，所以只限制同一位 Leader 底下不能重名。

**Q：version 怎麼設計？**
A：見上面第 3 節。從 1 開始，每次寫入加 1，UPDATE / DELETE 的 WHERE 要帶上讀到的版本，影響 0 列就回 412。

**Q：ON DELETE RESTRICT 要怎麼處理？**
A：見上面第 4 節。目前沒有刪帳號的功能，不用處理；將來要做時，在交易裡先處理提案，或改用軟刪除。

## 自我檢查

1. 把 `UNIQUE (leader_account_id, title)` 改成 `UNIQUE (title)` 會怎樣？
   → 整個平台的提案標題都不能重複，不同 Leader 也不能同名。

2. A、B 都讀到 version=3，A 的 PUT 先成功了，B 再帶 `If-Match: "3"` 送出 PUT，結果是什麼？
   → 412。B 有帶 `If-Match`，所以不是 428；但 DB 的 version 已經是 4，`WHERE version=3` 影響 0 列。
   428 問的是「有沒有帶」，412 問的是「帶的對不對」。

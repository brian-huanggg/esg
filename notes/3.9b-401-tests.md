# 3.9b 401 攔截與 RequireAuth 測試

## 目標與結果

用測試證明 3.9a 的行為：受保護路徑回 401 時會呼叫 handler，畫面跳回 `/login`；密碼錯和沒登入的 401 不會。

`make test`、`make lint-frontend`、`make format-frontend` 通過，前端 13 個測試全過（新增 7 個），後端覆蓋率 90.7%。

檔案：

- `frontend/src/api/client.test.ts`：4 個單元測試
- `frontend/src/auth/RequireAuth.test.tsx`：3 個整合測試

## 學到的概念

### 單元測試 vs 整合測試

分界是「有沒有拿掉其他零件」。

- 單元：`client.test.ts` 只測 `client.ts`，自己註冊假 handler，沒有 React、沒有 `AuthProvider`。像不載入 Spring context 的純 JUnit。
- 整合：`RequireAuth.test.tsx` 用真的 `AuthProvider`、`RequireAuth`、`MemoryRouter` 和 `api` client，只換掉最外層的 `fetch`。像 `@SpringBootTest` 加 `MockMvc`。

### 用 stub 換掉網路層

```ts
vi.stubGlobal('fetch', vi.fn(() => Promise.resolve(new Response('{}', { status: 401 }))))
```

每次回新的 `Response`，因為 body 只能讀一次。測完用 `vi.unstubAllGlobals()` 還原。

### 模組層級狀態會跨測試殘留

`onUnauthorized` 是模組變數，所以 `afterEach` 要 `setUnauthorizedHandler(null)`，否則上一個測試的 handler 會留到下一個。

### 整合測試抓得到單元測試抓不到的錯

單元測試只證明 `client.ts` 會呼叫 handler，不證明有人註冊。「受保護呼叫回 401 就跳回登入」這個整合測試，是唯一會因 `AuthProvider` 忘了註冊而失敗的。

### 測試用的受保護路徑

`/api/health` 只是 schema 裡有的路徑。測試只看路徑名稱，不看後端是否真的保護它。

## 自我檢查

**Q1：刪掉 `AuthProvider` 註冊 handler 的 useEffect，哪些測試會失敗？**
答案：只有「protected call 回 401 就跳回登入」這 1 個。`client.test.ts` 自己註冊 handler；前兩個 RequireAuth 測試只打 `/me`，在例外清單裡，不會用到 handler。

**Q2：`client.test.ts` 的 `afterEach` 為什麼要 `setUnauthorizedHandler(null)`？**
答案：`onUnauthorized` 是模組層級變數，會跨測試保留，不清掉會影響下一個測試。

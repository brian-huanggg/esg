# 1.10 第一條 GitHub Actions CI

> tag：`step-01-10`
> 檔案：`.github/workflows/ci.yaml`、`Makefile`、`frontend/package.json`
> 對應：PRD「CI Pipeline」（安全掃描放在 M11）

## 目標與結果

push 到 GitHub 後，CI 自動跑兩個平行的 job：

- `backend`：gen 一致性檢查 → `make test-backend`（含 80% 覆蓋率門檻）
- `frontend`：`npm ci` → gen 一致性檢查 → `make test-frontend` → `npm run build`

驗收：
- 正常 push：兩個 job 都是綠勾
- 故意把後端一個測試的預期值改錯：`backend` 的 `Test with coverage gate` 紅叉
  （`exit code 2`），`frontend` 仍是綠勾
- `git revert` 之後：回到綠勾

## 概念

GitHub Actions 只有三層：**workflow > job > step**（沒有 stage，那是 GitLab / Jenkins 的用語）。

```yaml
on:                      # 什麼事件觸發
  push:
    branches: [main]
  pull_request:          # 空值 = 任何分支的 PR 都觸發
jobs:
  backend:               # 一台全新的機器；沒有 needs: 就平行跑
    runs-on: ubuntu-latest
    steps:               # 依序執行，一步失敗後面就不跑
      - uses: actions/checkout@v6   # 呼叫別人寫好的 action
      - run: make test-backend      # 在機器上跑 shell 指令
```

- `run: |` 的 `|` 是 YAML 的多行文字記號，和 shell 管線無關。
- Cache：Go 的 `setup-go` 預設就開；Node 要寫 `cache: npm`。
  兩者都以 lock 檔（`go.sum`、`package-lock.json`）的雜湊值當 key。
  lock 檔不在 repo 根目錄時，要用 `cache-dependency-path` 指明。
- 版本只維持一份來源：`setup-go` 讀 `backend/go.mod`，`setup-node` 讀 `frontend/package.json` 的 `engines.node`
  （所以要先補上 `"engines": { "node": ">=24" }`）。
- **gen 一致性檢查**：CI 重新跑 `make gen-*`，再 `git diff --exit-code`。
  比較的是「commit 進來的 generated code」和「剛依 spec 重新產生的檔案」。
  有差異 → 回傳 1 → step 失敗。`--exit-code` 回傳 0 才是通過。
  限制：`git diff` 只看已追蹤的檔案，generated 檔已經 commit，所以夠用。
- `make gen` 拆成 `gen-backend` 和 `gen-frontend`，`gen` 依賴兩者。
  CI 和本機用同一個入口，每個 job 只需要自己的工具。

## 學習者提出的問題

- **`npm ci` 為什麼不用 `npm install`？** `npm install` 可能更新 lock 檔、裝到不同版本；
  `npm ci` 嚴格照 lock 檔、先刪 `node_modules` 重裝，lock 與 `package.json` 對不上就報錯。CI 要可重現。
- **`pull_request:` 空的可以嗎？** 合法，代表所有分支的 PR。`branches` 只是額外過濾 PR 的**目標分支**。
  `push` 要限定 `main`，避免同一份 commit 在 push 和 PR 各跑一次。
- **為什麼 `ubuntu-latest` 不是 Alpine？** `runs-on` 選的是 GitHub 提供的虛擬機（ubuntu / windows / macos），
  不是 container image。Ubuntu 預裝 `make`、`git`、GNU `sed`。Alpine 是做小 image 用的，M11 才會碰到。
- **Go 和 Node 的 gen 要不要分開？** 要，各自一個 job、各自一個 Makefile target。

## 這一步踩到的坑

- Makefile 的 recipe 一定要用 **Tab**，用空格會報 `missing separator`。
- `sed -i -e ...` 在 macOS（BSD sed）會把 `-e` 當成備份副檔名，報 `sed: -e: No such file or directory`；
  GNU sed（Ubuntu）則沒事。改成 `sed -e ... in > tmp && mv tmp in`，兩邊都能跑。
- `vitest: command not found`（exit 127）：`frontend/node_modules` 沒裝。CI 裡由 `npm ci` 負責，本機要自己跑。
- Job 失敗時，`setup-go` 的 Post step 會被跳過（不儲存 cache）。

## 自我檢查

**Q：改了 `api/openapi.yaml` 卻忘了 `make gen` 就 push，哪個 job 的哪個 step 會失敗？**

A：`backend` 的 `Generated code matches spec` 和 `frontend` 的 `Generated types match spec`，**兩個 job 都紅**。
spec 是新的，但 commit 進來的 generated code 是舊的；CI 重新產生後和 checkout 的內容有差異，
`git diff --exit-code` 回傳 1。

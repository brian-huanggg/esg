# 3.5b 登出 `DELETE /api/sessions/current`

## 目標與結果

登出做兩件事：刪掉 DB 的 session，並讓瀏覽器清掉 Cookie。

- 有效 Cookie → 204，帶 `Set-Cookie: session=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax`
- 沒登入 → 401（由 3.6a middleware 擋下）
- 同一個 token 再打 `/api/accounts/me` → 401

檔案：

- `api/openapi.yaml`：`204` 加上 `Set-Cookie` header（規格先行），再 `make gen`
- `backend/internal/auth/handler.go`：`DeleteCurrentSession`、`clearedSessionCookie`、`sessionDeleter` 介面
- `backend/internal/shared/middleware/auth.go`：新增 `WithTokenHash`，給 handler 測試用
- `backend/cmd/api/main.go`：`NewSessionHandler` 多傳 `sessionRepo`，`Authenticate` map 加 `DeleteCurrentSession`
- `backend/internal/auth/handler_test.go`：`fakeSessionDeleter`、`TestDeleteCurrentSession`（3 個情境）

## 學到的概念

### 登出要同時處理伺服器和瀏覽器

只清 Cookie 不刪 DB：token 被複製出去的人仍可冒用，直到過期。所以先 `sessions.Delete(tokenHash)`，再回清除用的 Set-Cookie。

Spring 對應：`SecurityContextLogoutHandler` 加 `CookieClearingLogoutHandler`。Go 沒有 logout filter，要在 handler 自己寫。

### 清 Cookie 的方式

```go
c := http.Cookie{Name: "session", Path: "/", MaxAge: -1, HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode}
```

- 瀏覽器用 Name + Domain + Path 辨識 Cookie，Path 不一樣就是另一顆，舊的清不掉
- `MaxAge: -1` 才會輸出 `Max-Age=0`；`MaxAge: 0` 代表「不設定」

### 防禦性檢查

middleware 已保證受保護路由的 ctx 有 `tokenHash`。handler 仍檢查 `TokenHashFrom` 的 `ok`，避免 `main.go` 漏設保護時，匿名請求變成可呼叫的登出。

### Go 手動接線

新增依賴要自己改 `NewSessionHandler` 簽名、在 `main.go` 傳入。Spring 由 `@Autowired` 完成。多寫的是刻意的明確性。

## 遇到的問題

- 測試用的 `fakeSessions` 和 `service_test.go` 同名，編譯錯誤 `fakeSessions redeclared`。同一個 package 的所有 `_test.go` 共用命名空間，改名為 `fakeSessionDeleter`
- 建構式多一個參數，`newTestHandler` 和 `TestGetCurrentAccount` 都要補
- `TestStubsReturn501` 在 `DeleteCurrentSession` 實作後不再成立，整個刪除

## 自我檢查

1. `clearedSessionCookie()` 的 Path 寫成 `/api`（登入是 `/`）會怎樣？
   答：瀏覽器的舊 Cookie 不會被清掉，因為 Path 不同被當成另一顆 Cookie。
2. 只清 Cookie、不刪 DB session，最主要的風險？
   答：其他人拿到舊 token 仍可冒用登入，直到過期。

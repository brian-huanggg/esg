# Keyset 與 Offset 分頁

**Offset：**

```sql
SELECT * FROM proposals
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 9980;
```

資料庫必須**先走過 9,980 列再丟掉**，只回傳最後 20 列。成本隨 offset 線性增長，翻越深越慢。

**Keyset（又稱 cursor / seek 分頁）：**

```sql
SELECT * FROM proposals
WHERE created_at < :last_created_at
   OR (created_at = :last_created_at AND id < :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

客戶端帶回「上一頁最後一筆」的位置，資料庫用索引直接**跳到那個位置**往後讀 20 筆。成本固定，與頁碼無關。這裡用展開的 `OR` 寫法，而不是 `(a,b) < (x,y)`，是因為後者在混合排序方向時優化器可能用不上索引。

| | Offset | Keyset |
| --- | --- | --- |
| 深分頁效能 | 越翻越慢 | 恆定 |
| 資料變動時 | 有新增或刪除會**漏看或重複看到**某些列 | 穩定 |
| 跳到第 N 頁 | 可以 | 不行，只能上一頁、下一頁、載入更多 |
| 總筆數 | 容易（但 `COUNT` 本身也貴） | 需要另外算 |
| 排序彈性 | 任意欄位 | 需要**唯一且確定**的排序（要加 `id` 當 tie-breaker），每種排序最好有對應的複合索引 |
| 實作 | 簡單 | 要設計不透明的 cursor（通常是 base64 編碼，不要讓前端自己拼） |

**對你專案的務實判斷：** PRD 的情境是 10,000 筆、每頁最多 100 筆。這個規模下，offset 即使翻到最後一頁也只是毫秒級的差距，**不是瓶頸**。Keyset 真正划算的時機是資料到十萬、百萬筆，或是做無限捲動的時候。

## Keyset的代價

1. 失去跳頁：只能上一頁、下一頁。如果使用者要「直接跳到第 5 頁」，做不到。
2. 排序受限：每一種排序都需要唯一且確定的排序鍵（要補 id 當 tie-breaker），而且最好每種排序都有一個對應的複合索引。PRD 要求「篩選和排序」，組合一多，索引數量會爆炸，每個索引也會拖慢寫入。
3. 總筆數與頁數：UI 常想顯示「共 237 筆，第 3/12 頁」，Keyset 不直接支援。
4. 實作複雜：要設計 cursor 的編碼、驗證與過期，處理「上一頁」的反向查詢，還要考慮 cursor 帶的值被改動的安全性。
5. 前端要配合：UI 得是「載入更多」或「上下頁」的樣式，不是頁碼。

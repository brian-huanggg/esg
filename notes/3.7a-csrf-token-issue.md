# 3.7a 登入時發 CSRF token

## 目標與結果

登入成功後，回應帶兩個 `Set-Cookie`：`session`（HttpOnly）和 `csrf_token`（JS 可讀）。`sessions` 表多一欄 `csrf_token_hash`，只存雜湊。這一步**還不驗證**，驗證在 3.7b。

驗收（curl）：

- `POST /api/sessions` 回 201，有兩行 `Set-Cookie`
- `csrf_token` 沒有 `HttpOnly`，`session` 有
- `make test` 通過，後端覆蓋率 89.7%

檔案：

- `api/openapi.yaml`：登入 201 拿掉 `Set-Cookie` header 宣告，改在 description 說明兩個 cookie
- `backend/migrations/000003_add_csrf_token_hash.{up,down}.sql`：新增欄位
- `backend/internal/session/repository.go`：`Create` 多收 `csrfHash`
- `backend/internal/auth/service.go`：`Tokens` 型別、`newToken` helper，`Login` 回傳兩個 token
- `backend/internal/auth/handler.go`：`createSessionResponse`、`csrfCookie`
- 三個對應的測試檔

## 學到的概念

### CSRF 與 token

瀏覽器會自動帶 cookie，所以惡意網站可以讓你的瀏覽器替你送請求。解法是要求請求多帶一個攻擊者拿不到的值（`X-CSRF-Token` header）。

| 做法 | 驗證方式 | Spring 對應 |
| --- | --- | --- |
| Synchronizer token | 伺服器存 token，比對 header | `HttpSessionCsrfTokenRepository` |
| Double-submit | cookie 與 header 相同 | `CookieCsrfTokenRepository` |

我們選 synchronizer 的 DB 版：伺服器存雜湊，驗證時把 header 的值雜湊後比對。

`SameSite` 不夠：`Lax` 只擋部分跨站請求，瀏覽器行為有差異，同站子網域被入侵時也擋不住。它是第一層，CSRF token 是第二層。

### 三個 cookie 屬性管三件事

| 屬性 | 管什麼 |
| --- | --- |
| `Secure` | 只經由 HTTPS 傳送 |
| `HttpOnly` | JS 能不能讀（防 XSS 偷 token） |
| `SameSite` | 跨站請求會不會帶上 cookie |

### 為什麼 `csrf_token` 不設 HttpOnly

DB 版只存雜湊，伺服器之後拿不回原始值，所以 token 只有登入那一刻能交給瀏覽器。前端之後要放進 `X-CSRF-Token`，必須能從 cookie 讀到，所以不能 HttpOnly。

兩個 token 必須獨立。若 CSRF token 等於 session token，JS 可讀的 cookie 就等於洩漏 session token。

### 一個回應發兩個 Set-Cookie

oapi-codegen 產生的 header 欄位是單一字串，內部用 `Header().Set`，會覆蓋。解法是自己實作 response 型別：

```go
type createSessionResponse struct {
	api.CreateSession201JSONResponse
	tokens Tokens
}

func (r createSessionResponse) VisitCreateSessionResponse(w http.ResponseWriter) error {
	w.Header().Add("Set-Cookie", sessionCookie(r.tokens.Session))
	w.Header().Add("Set-Cookie", csrfCookie(r.tokens.CSRF))
	return r.CreateSession201JSONResponse.VisitCreateSessionResponse(w)
}
```

- 嵌入（embedding）讓 body 的寫入沿用產生的邏輯。
- 外層同名方法遮蔽內層。
- cookie 要在內層 `WriteHeader` 之前加。
- spec 不能再宣告 `Set-Cookie` header，否則內層的 `Set` 會蓋掉我們的 `Add`。

Spring 對應：`HttpServletResponse.addCookie` 可以呼叫多次。Go 裡要自己接線，多寫的程式碼是刻意的明確性。

### 測試帶 `Visit` 的 response

cookie 不在 struct 欄位裡，要真的呼叫 `VisitCreateSessionResponse` 寫進 `httptest.NewRecorder()`，再用 `rec.Header().Values("Set-Cookie")` 檢查。

## 問題與解答

- **Q：為什麼要自訂 response 型別？** 產生的型別只能發一個 `Set-Cookie`。
- **Q：測試一開始為什麼失敗？** `service_test.go` 把 CSRF 雜湊拿去和 `sessions.tokenHash` 比，寫錯欄位。兩個 token 獨立，所以一定不相等，測試正確地失敗。也說明了「兩者獨立」的斷言有價值：若 `Login` 把同一個 hash 傳兩次，寫錯的測試反而會過。

## 自我檢查

1. 為什麼 `csrf_token` 不設 HttpOnly，`session` 要設？答：前端 JS 必須讀到 `csrf_token` 再放進 `X-CSRF-Token`；`session` 則要防 XSS 偷走。（第 3 次答對。常見誤解：`Secure` 不管 JS 讀取，`HttpOnly` 也不管跨站是否帶 cookie。）
2. 若 `Login` 把同一個 hash 傳給兩個欄位，最主要的問題？答：JS 可讀的 cookie 等於洩漏 session token。（第 1 次答對。）

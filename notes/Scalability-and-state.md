# State

## 為什麼有沒有「狀態」如此重要

因為**狀態決定了你能不能「複製」**。

擴容、容錯和部署，本質上都在做同一件事：複製出更多一模一樣的實例，並且隨時能換掉任何一個。無狀態的程式可以任意複製和替換，有狀態的程式不行。

**一個反例：** 假設 Session 存在後端 A 的記憶體裡。

```text
使用者登入 ─> LB ─> 後端 A（Session 存在 A 的記憶體）
下一個請求 ─> LB ─> 後端 B（B 沒有這個 Session → 401，使用者被踢出）
```

為了讓它能運作，你只剩下幾條路，每條都有代價：

| 做法 | 代價 |
| --- | --- |
| Sticky session（LB 把同一使用者固定導到同一台） | 負載不均；那台掛了，所有人在上面的使用者全被登出 |
| 後端之間同步 Session | 複雜，而且是「狀態」問題換了個形式 |
| 不擴容 | 失去水平擴展和高可用 |
| **把狀態搬到共用的地方** | 這就是無狀態架構，也就是 PRD 把 Session 放 MariaDB 的原因 |

**無狀態帶來的具體好處：**

1. **水平擴展很簡單**：流量大就多開幾個 pod。
2. **容錯**：任何一個 pod 隨時掛掉，LB 換一個就好，使用者無感。
3. **零停機部署**：滾動更新時舊 pod 一個一個被換掉，不會有人因此丟失進度。
4. **自動伸縮**：Kubernetes 的 HPA 能放心縮放，因為縮掉哪一個都沒差。
5. **好測試、好除錯**：同樣的輸入給任何一個實例，結果都一樣。

**但要誠實看到另一面：狀態並沒有消失，只是被集中了。** 無狀態的後端讓「難的部分」都推給了 DB、MinIO、Vault。這些有狀態的元件反而變成最難擴展的地方（回想上一輪 Galera 的寫入瓶頸、熱點 row）。

所以架構設計的核心心法是：**盡量縮小有狀態的部分，並且明確知道它們在哪裡。** 你的 PRD 做得很好，狀態只存在三個地方，其餘全部可以隨意複製。

順帶一個容易忽略的點：**本機磁碟也是狀態**。如果簡報檔存在後端的本機磁碟，使用者上傳到 A，下載請求落到 B 就找不到。這正是 V0 的單機版要搬到 V1 時，必須引入 MinIO 的原因。

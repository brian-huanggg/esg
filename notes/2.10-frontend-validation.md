# Step 2.10 前端欄位驗證與伺服器錯誤

## 目標與結果

`/register` 送出前先擋明顯錯誤（工號不是 6 位數字等）；後端回 409 / 422 時，
錯誤顯示在對應欄位旁。新增 `Register.test.tsx`，`make test` 通過，M2 里程碑在瀏覽器走完。
對應 PRD 2.1 帳號。

## 學到的概念

### 前端驗證只是 UX

前端驗證像電梯門的感應器：先擋明顯問題，但真正的檢查在後端
（Spring 的 `@Valid`）。後端永遠要重驗，因為任何人都能繞過瀏覽器直接打 API。
刪掉前端 `validate()`，後端 422 仍擋下不合格資料，只是使用者多等一趟往返。

### 兩種錯誤，一份狀態

前端驗證和伺服器錯誤都寫進同一份 `fieldErrors`，畫面只讀這一份。
不屬於任何欄位的錯誤（網路、500）放在 `formError`。

```tsx
type FieldErrors = Partial<Record<'employeeId' | 'name' | 'password', string>>
```

### 三條失敗路徑

1. `api.POST` 回 `error`（HTTP 4xx/5xx）：用 `error.code` 分流（409 `EMPLOYEE_ID_TAKEN`、422 `VALIDATION_FAILED` + `fields`）
2. `fetch` 本身失敗（斷網）：`openapi-fetch` 會 **throw**，要 `try/catch`
3. 成功：`done`

HTTP 錯誤是「回傳值」，網路錯誤是「例外」，兩條機制不同，都要接。
這跟 Go 的 `if err != nil` 逐項處理是同一種思路。

### 測試環境的兩個坑

1. **相對 URL**：`openapi-fetch` 內部 `new Request('/api/accounts')`。瀏覽器會補成完整網址，
   Node（undici）不會，直接 throw `Failed to parse URL`。解法：`createClient({ baseUrl: window.location.origin })`。
2. **fetch 在建立時被綁定**：`createClient` 預設 `fetch: baseFetch = globalThis.fetch`，
   在 import 時就存起來，之後 `vi.stubGlobal('fetch', ...)` 來不及。解法：傳
   `fetch: (req) => globalThis.fetch(req)`，每次呼叫才查。
   類比 Spring：bean 在啟動時就綁定依賴，事後換 mock 不會生效。

```ts
export const api = createClient<paths>({
  baseUrl: window.location.origin,
  fetch: (req) => globalThis.fetch(req),
})
```

### 測試「碰巧通過」不等於測到對的路徑

修正前，「fetch throws」測試是通過的，因為無效 URL 的 throw 也走 `catch`。
測試通過時，要問它是不是因為「我以為的原因」通過。

## 學習者的問題與解答

- **為什麼 409 / 422 的測試 DOM 顯示 `Network error`？** `api.POST` 在測試裡 throw，被 `catch` 接住。
  先是相對 URL，修掉後是真的 `fetch` 被呼叫（stub 太晚）。
- **為什麼 lint 報 `'e' is defined but never used`？** 除錯用的 `catch (e)` 沒改回 `catch {`。

## 自我檢查

1. 刪掉前端 `validate()`、只靠後端 422，會怎樣？
   答：只是體驗變差。後端 422 仍擋下不合格資料。
2. 修正前，第 4 個測試為什麼不可靠？
   答：`catch` 被別的 throw（無效 URL）觸發，不是被 mock 的 `fetch` 失敗觸發。

# 3.8a CSRF middleware 與登入頁

## 目標與結果

前端寫入類請求自動帶 `X-CSRF-Token`，並有一個登入頁。在瀏覽器登入後：

- 錯誤密碼：頁面顯示後端錯誤訊息，`POST /api/sessions` 回 401
- 正確密碼：回 201，導到 `/`，Cookies 有 `session`（HttpOnly）和 `csrf_token`（非 HttpOnly）
- 登入請求本身沒有 `X-CSRF-Token`（當時 cookie 還不存在，登入端點也不檢查 CSRF）

`make test`、`make lint-frontend`、`make format-frontend` 通過，後端覆蓋率 90.7%。

檔案：

- `frontend/src/api/client.ts`：`SAFE_METHODS`、`readCookie`、`api.use` 掛 middleware
- `frontend/src/pages/Login.tsx`：登入表單
- `frontend/src/App.tsx`：新增 `/login` 路由

## 學到的概念

### Cookie 由瀏覽器自動帶
同源的 `fetch` 預設 `credentials: 'same-origin'`，會自動帶 cookie。`session` 是 HttpOnly，JS 讀不到也不需要讀。

### 雙重提交（double-submit）CSRF
瀏覽器會自動帶 cookie，所以惡意網站也能讓瀏覽器送出帶 cookie 的請求。但惡意網站讀不到我們網站的 cookie，無法在 header 放正確的值。後端要求 `X-CSRF-Token` header 等於 `csrf_token` cookie，所以 `csrf_token` 刻意不設 HttpOnly，讓我們的 JS 讀它。

### openapi-fetch middleware
Spring 類比：`ClientHttpRequestInterceptor`。差別是 Spring 靠容器掃描註冊，這裡要自己呼叫 `api.use(...)`，是刻意的明確性。

```ts
api.use({
  onRequest({ request }) {
    if (SAFE_METHODS.has(request.method)) return
    const token = readCookie('csrf_token')
    if (token) request.headers.set('X-CSRF-Token', token)
  },
})
```

### 讀 cookie
`document.cookie` 是一整串字串（`a=1; csrf_token=xyz`），要自己 `split('; ')` 再找。找不到時 `pair?.slice(...)` 回 `undefined`，型別 `string | undefined` 逼你處理沒有 cookie 的情況（類比 `Optional<String>`）。

### useNavigate
React Router 的 hook，回傳導頁函式。`navigate('/')` 只切換路由，不重新載入頁面。

## 自我檢查

1. 登入請求的 Request Headers 為什麼沒有 `X-CSRF-Token`？
   答：登入當下 `csrf_token` cookie 還不存在，`readCookie` 回 `undefined`，`if (token)` 不成立。（常見誤解：以為 POST 被當成 safe method，其實 `SAFE_METHODS` 只有 GET / HEAD / OPTIONS。）
2. 後端若把 `csrf_token` 改成 HttpOnly，會怎樣？
   答：`document.cookie` 讀不到它，之後的 POST / DELETE 都沒有 header，被後端 CSRF 檢查擋下。

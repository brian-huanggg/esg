# 3.7b middleware 驗證 X-CSRF-Token

## 目標與結果

寫入類請求（非 GET / HEAD / OPTIONS）必須帶 `X-CSRF-Token`，middleware 把它雜湊後和 `sessions.csrf_token_hash` 比對。失敗回 403 `CSRF_FAILED`。登出時兩個 cookie（`session`、`csrf_token`）都要清掉。

驗收（curl，六個情境）：

| 情境 | 結果 |
| --- | --- |
| `DELETE` 沒帶 header | 403 |
| `DELETE` 帶錯的 token | 403 |
| 沒登入的 `DELETE` | 401（401 優先於 CSRF） |
| `GET /api/accounts/me` | 200（GET 免 token） |
| `DELETE` 帶對的 token | 204，兩行 `Set-Cookie`，各自 `Max-Age=0` |
| 登出後再打 `/me` | 401 |

`make test` 通過，後端覆蓋率 90.7%。

檔案：

- `api/openapi.yaml`：新增 `components.responses.Forbidden`，登出加 403
- `backend/internal/session/repository.go`：`FindActive` 回傳 `Active{AccountID, CSRFTokenHash}`
- `backend/internal/shared/middleware/auth.go`：`isSafeMethod`、`csrfValid`，`Authenticate` 加 CSRF 檢查
- `backend/internal/auth/handler.go`：`deleteSessionResponse`、`clearedCSRFCookie`
- 三個對應的測試檔

## 學到的概念

### 錯誤檢查順序：401 先於 CSRF

PRD 5.2 規定 401 → CSRF → 404 → …。實作上就是 `FindActive` 之後才驗 CSRF，所以沒登入的 `DELETE` 會回 401，不是 403。

### constant-time 比對

```go
sum := sha256.Sum256([]byte(token))
ok := subtle.ConstantTimeCompare(sum[:], wantHash) == 1
```

`==` 和 `bytes.Equal` 遇到第一個不同的 byte 就提早結束，回應時間會洩漏資訊。`ConstantTimeCompare` 永遠比完整個長度。注意回傳的是 `int`，`1` 才是相等。

Spring 對應：`CsrfFilter` 加 `MessageDigest.isEqual`。Spring 預設自動啟用，Go 要自己寫。

### 回傳多個值時包成 struct

`FindActive` 需要回傳 account id 和 CSRF 雜湊。超過兩個值時，Go 慣例是包成 struct（類似 Java 的 DTO / record），不寫成 `(int64, []byte, error)`。

### 自訂 response 型別（第二次）

產生的 `DeleteCurrentSession204Response` 用 `Header().Set`，只能發一個 `Set-Cookie`。登出要清兩個，所以自己寫：

```go
type deleteSessionResponse struct{}

func (deleteSessionResponse) VisitDeleteCurrentSessionResponse(w http.ResponseWriter) error {
	w.Header().Add("Set-Cookie", clearedSessionCookie())
	w.Header().Add("Set-Cookie", clearedCSRFCookie())
	w.WriteHeader(http.StatusNoContent)
	return nil
}
```

只要實作那個方法就滿足介面，不用寫 `implements`（Go 的 implicit interface）。跟 3.7a 的 `createSessionResponse` 同一種手法。

### 清 cookie 的規則

瀏覽器用名稱、Domain、Path 判斷是不是同一個 cookie。清除時 `Path` 必須和發的時候相同，否則過期指令作用在另一個 cookie 上。`MaxAge: -1` 會序列化成 `Max-Age=0`。`csrf_token` 沒有 `HttpOnly`，因為前端 JS 要讀它。

## 我提出的問題與解答

- 測試怎麼改：`FindActive` 的回傳型別變了，只有 `TestFindActive_Valid` 需要改；`[]byte` 不能用 `==`，要用 `bytes.Equal`。
- `make test` 在 `cmd/api` 編譯失敗：`main.go` 把 repository 傳給 `Authenticate`，介面簽名還是舊的，改完 middleware 就好了。
- 第一次 curl 全部 401：用到舊的 session（閒置超過 30 分鐘），重新登入後正常。
- `TestDeleteCurrentSession` 改完後 401 和 500 的 case 消失：替換 `switch` 的 `case` 時範圍切太多，要補回。

## 自我檢查

**1. 如果把 `Touch` 放回 CSRF 檢查之前，會有什麼實際影響？**

答：被擋下的偽造請求也會延長 session。請求仍回 403，但 `last_seen_at` 被更新。被擋下的請求不該有任何副作用。

**2. 登出時 `clearedCSRFCookie` 的 `Path`、`Secure`、`SameSite` 為什麼要和發 cookie 時一樣？**

答：瀏覽器用名稱、Domain、Path 認定是不是同一個 cookie。屬性對不上時，過期指令只會作用在另一個 cookie 上，原本的 cookie 清不掉。

（第一次兩題都答錯，錯選項分別是「CSRF 驗證會失效」和「Go 的 `http.Cookie` 要求兩邊欄位相等才能序列化」。`Touch` 在哪裡執行不影響 CSRF 檢查本身；`Cookie.String()` 只是照欄位格式化，不會比對。）

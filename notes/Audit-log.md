# Audit Log Design

我先讀一下專案的 PRD,確認專案規模再回答。

先說結論:以 ESG 這個專案的規模(公司內部、一個團隊最多 5 人、列表壓測 10,000 筆、單一 Go 模組化單體),Audit Log 最合適的做法是**「同一個資料庫 transaction 內同步寫入」**。企業級的做法是為了解決你現在還遇不到的問題。

## 兩種規模的差異

| 面向 | 中小型(本專案) | 大型企業級 |
| --- | --- | --- |
| **寫入方式** | 與業務資料在**同一個 transaction** 同步寫入 | **Transactional Outbox** → 訊息佇列(Kafka 等)→ 獨立的稽核服務 |
| **一致性** | 強一致:稽核失敗,整筆操作回滾 | 最終一致:業務先成功,稽核事件保證「最終會到」 |
| **儲存位置** | 同一個 MariaDB 的 `audit_log` 表 | 獨立資料庫、WORM 儲存(如 Object Lock)、SIEM |
| **防竄改** | 選配(你的加分項 hash chain) | 必備:簽章(KMS/HSM)、定期把雜湊錨定到外部系統 |
| **權限分離** | Admin 能查,應用程式帳號只有 `INSERT` | DBA、開發、稽核者三方分離,稽核紀錄本身也被稽核 |
| **事件格式** | 自訂欄位 | 全公司統一 schema、有版本管理,方便跨系統關聯 |
| **查詢** | SQL + 索引 + 分頁 | Elasticsearch / SIEM,支援全文搜尋與告警 |
| **保存與合規** | 沒有明確要求 | 保存年限、冷熱分層、PII 遮罩、SOX / ISO 27001 稽核 |
| **失敗策略** | 一律 fail-closed | 依風險分級:高風險 fail-closed,低風險先寫本機緩衝再補送 |

## 為什麼你的專案選同步寫入是對的

你的 PRD 有一條硬規則:「不允許出現沒有稽核紀錄的成功寫入」。要保證這件事,最簡單可靠的方法就是讓稽核和業務資料**共用同一個 transaction**,資料庫會替你保證兩者同生同死。

企業級改用 Outbox + 佇列,是因為它們面對的是:

- 稽核事件量太大,會拖垮主資料庫。
- 有幾十個服務,不可能每個都直接寫同一張表。
- 稽核系統要獨立部署,不能被業務團隊改動。

代價是複雜度大增:要處理重複事件、事件順序、佇列積壓和補送。你的專案沒有這些痛點,引入它們就是過度設計。

## 針對本專案的三個提醒

1. **被拒絕的嘗試要用獨立 transaction。** 一個被 403 或 404 擋下的請求,沒有業務 transaction 可以搭便車,所以稽核要自己開一個 transaction 寫入。如果這次寫入也失敗,就回 500 或 503,不能靜默吞掉。這是「同步寫入」模型中最容易漏掉的角落。

2. **hash chain 在 Galera 上有陷阱。** hash chain 要求每筆紀錄引用上一筆的雜湊,所以所有寫入都會去搶「最後一筆」這個熱點。在 Galera 多主架構下,並發寫入同一列容易觸發 certification conflict(類似 deadlock),寫入也被迫串行化。以你的流量(註冊、登入、提案寫入)這不是大問題,但要預先設計:例如寫入時重試,或固定只寫其中一個節點。企業級系統常改成「分區獨立 chain」或「批次建 Merkle tree」,就是為了避開這個瓶頸。

3. **現在就要留好擴充的接縫。** 把所有稽核寫入收斂在 `audit` 模組的單一介面,例如 `Record(ctx, tx, event)`,事件格式也固定下來。日後真的要升級成 Outbox,只需要換這個介面背後的實作,呼叫端完全不用改。

## 思考方式

principal engineer 不會問「企業怎麼做」,而是問:

> **我現在的規模、風險和合規要求,值得付出多少複雜度?**

選型的依據是你面對的問題,而不是別人的架構。你現在的選擇已經夠用,而且保留了升級的路徑。

# 4.2 migrate image

## 目標與結果

把 `migrate` 工具和 `backend/migrations/*.sql` 打包成獨立的 image，之後給 K8s Job（Step 4.8）和 compose（Step 4.4）使用。

驗收：對 compose 的 MariaDB 執行 `up`，輸出 `no change`（DB 已經是最新版本，連線與讀檔都成功）。

新增檔案：`backend/Dockerfile.migrate`

```dockerfile
FROM migrate/migrate:v4.18.3
COPY migrations /migrations
ENTRYPOINT ["migrate", "-path", "/migrations"]
```

執行方式：

```bash
docker build -f backend/Dockerfile.migrate -t esg-migrate:dev backend
docker run --rm esg-migrate:dev \
  -database "mysql://$DB_USER:$DB_PASSWORD@tcp(host.docker.internal:3306)/$DB_NAME" up
```

## 學到的概念

- **migrate image**：把工具和 SQL 檔打包在一起。image tag 就是 schema 版本。類比 Spring 的 Flyway Docker image 加上 SQL 資料夾。
- **為什麼獨立成 image**：backend 是 distroless，沒有 shell 也沒有 `migrate`。migration 獨立後，backend 不必在啟動時改 schema，多個 replica 也不會同時搶著改。
- **`ENTRYPOINT` 與 `CMD`**：傳入的參數會**附加**在 `ENTRYPOINT` 後面，但會**整個取代** `CMD`。固定不變的部分（`-path`）放 `ENTRYPOINT`，每個環境不同的部分（`-database`、`up`）由呼叫端傳入。
- **exec 形式不展開環境變數**：`CMD ["...", "${X}"]` 不經過 shell，migrate 會收到字面上的 `${X}`。所以 DSN 必須由呼叫端用 args 傳入。
- **密碼不寫進 image**：寫進 Dockerfile 會留在 layer 裡，任何能 pull 的人都拿得到，而且各環境的 DSN 本來就不同。

## 問題與解答

**什麼是 migrate image，優缺點？**
優點：版本與 backend 綁定、目標環境不用安裝工具、backend 保持精簡、各環境行為一致。缺點：多一個 image 要維護，SQL 改了就要重新 build。

**為什麼用 `ENTRYPOINT` 而不是 `CMD`？**
用 `CMD` 時，`docker run esg-migrate -database ... up` 會取代整個指令，Docker 會去執行 `-database`。用 `ENTRYPOINT` 則會變成 `migrate -path /migrations -database ... up`。

## 自我檢查

1. 把 `ENTRYPOINT` 改成 `CMD` 再傳入 `-database ... up`，會怎樣？
   答：容器啟動失敗。參數取代整個 CMD，Docker 會去找 `-database` 這個程式。
2. 為什麼 DSN 不直接寫進 Dockerfile？
   答：image 會帶著密碼，任何能 pull 的人都拿得到；而且各環境的 DSN 本來就不同。

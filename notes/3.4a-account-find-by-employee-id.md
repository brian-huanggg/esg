# 3.4a account：用工號查帳號

## 目標與結果

`account.Repository` 新增 `FindByEmployeeID`，給工號回傳完整的 `*Account`，查不到回 `ErrNotFound`。
這是 3.4b（auth service）登入時的前置：service 需要 `ID`（內部 BIGINT）和 `PasswordHash`。
3.4 原本是一步，因為還需要這個 repository 方法，行數會超過預算，所以拆成 3.4a / 3.4b。

檔案：

- `backend/internal/account/repository.go`：`Account.ID`、`ErrNotFound`、`FindByEmployeeID`
- `backend/internal/account/repository_test.go`：`Found`、`NotFound` 兩個整合測試

## 學到的概念

### sentinel error 隔離儲存層

```go
if errors.Is(err, sql.ErrNoRows) {
	return nil, ErrNotFound
}
```

把 `sql.ErrNoRows` 換成 `account.ErrNotFound`，`auth.Service` 只需要認識 account 套件的錯誤，
不用 `import "database/sql"`。以後換儲存方式，service 不用改。
Spring 類比：`Optional.empty()` / `EmptyResultDataAccessException`。

### Scan 依位置賦值

```go
.Scan(&a.ID, &a.UUID, &a.EmployeeID, &a.Name, &a.PasswordHash, &a.CreatedAt)
```

`Scan` 的參數是 `...any`，編譯器不檢查它和 `SELECT` 欄位的對應。
欄位順序不一致時，型別不相容會在執行期回傳錯誤；型別相容則值悄悄放進錯的欄位。
所以測試要比對欄位值，不能只檢查 `err == nil`。
Spring 的 ORM 自動對應，Go 要手動接線，這是刻意的明確性。

### 內部與對外的 ID

`Account.ID`（BIGINT）只在內部使用，例如傳給 `session.Create`；對外一律用 `UUID`。

## 問題與解答

- Q：為什麼 `FindByEmployeeID` 不放進 service？
  A：它只負責查資料，是 repository 的職責。service 之後用 interface 接它，測試時換成 fake。

## 自我檢查

1. 為什麼把 `sql.ErrNoRows` 換成 `account.ErrNotFound`？
   答：避免 service 依賴 `database/sql`，隔離儲存層細節。（不是效能，也不是編譯要求）
2. `SELECT` 欄位順序和 `Scan` 參數順序不一致會怎樣？
   答：編譯通過，執行期才出問題：型別不相容回傳錯誤，相容則值放錯欄位。（不是編譯錯誤，也不是 `ErrNoRows`）

# 5.6 列表 API 的規格與 repository：分頁、排序白名單、搜尋

## 目標與結果

`api/openapi.yaml` 新增 `GET /api/proposals?page&page_size&sort&order&q`，
`Repository.List` 能回傳「這一頁的提案 + 符合條件的總數」。
handler 先放 501 stub，真正的實作留到 5.7。

整合測試證明：同值排序穩定、`page_size` 上限 100、`%` 與 `_` 當成普通字元、
只看得到自己的提案、未知的 `sort` / `order` 會被拒絕。

## 學到的概念

### 1. `ORDER BY ?` 綁的是值，不是欄位名

```go
// 錯：綁定的 "title" 會變成字串常數 'title'，每一列的排序鍵都一樣
db.Query(`SELECT ... ORDER BY ?`, "title")

// 對：欄位名只能來自白名單 map，再用 Sprintf 拼進 SQL 文字
var sortColumns = map[string]string{
    "createdAt": "created_at",
    "updatedAt": "updated_at",
    "title":     "title",
}
col, ok := sortColumns[p.Sort]
```

使用者的字串永遠進不了 SQL 文字，只有白名單裡的值可以。
`LIMIT ? OFFSET ?` 和 `LIKE ?` 是「值」，照常用 `?` 綁定。

Spring 類比：`Pageable` / `Sort` 會自動檢查欄位。Go 沒有，白名單要自己寫。

### 2. 用 `id` 當 tie-breaker

```sql
ORDER BY title ASC, id ASC
```

排序鍵相同的列，資料庫不保證相對順序。翻第 1 頁和第 2 頁是兩次獨立查詢，
順序可能不同，導致同一筆出現兩次或整筆消失。加上唯一的 `id`，順序就是確定的。

### 3. `LIKE` 要先跳脫

```go
func escapeLike(s string) string {
    return strings.NewReplacer(`\`, `\\`, `%`, `\%`, `_`, `\_`).Replace(s)
}
args := []any{leaderID, "%" + escapeLike(p.Q) + "%"}
```

使用者搜尋 `50%` 時，`%` 不能變成「任意字串」。先跳脫，再用 `?` 綁定。

### 4. 共用 WHERE 的兩次查詢

`COUNT(*)` 和 `SELECT` 共用同一個 `where` 與 `args`，所以 `total` 和 `items` 的過濾條件一致。
兩次查詢之間資料可能被改動，`total` 可能與 `items` 差一筆；列表顯示用，可以接受。

### 5. Go 要手動做的事

- 手動檢查 `sort` / `order`、手動算 `offset`、手動夾住 `page_size`
- `for rows.Next()` 結束後一定要檢查 `rows.Err()`，迴圈可能因為連線中斷而提早結束
- 手動 `Scan` 每個欄位

### 6. 為什麼要加 501 stub

`make gen` 後 `StrictServerInterface` 多了 `ListProposals`。`main.go` 嵌入的
`*ProposalHandler` 沒有這個方法就編譯失敗，所以先放一個回 501 的 stub（同 5.2）。

## 學習者的問題與決定

- 問：`q` 要搜哪些欄位？答：只搜 `title`。列表頁只顯示標題，這一步也比較單純。

## 自我檢查

1. 如果 `List` 用 `ORDER BY ?` 並把 `"title"` 當參數綁定，會怎樣？
   - 答案：依字串常數排序，每一列排序鍵相同，順序形同未定義。
   - 第一次選了「正常依 title 排序」，誤把「值」當成「欄位名」。
2. 為什麼 `ORDER BY title ASC, id ASC` 而不是只有 `title ASC`？
   - 答案：讓排序鍵相同的列有固定順序，分頁邊界才穩定。
   - 第一次選了「防 SQL injection」。防線其實是白名單和 `?` 綁定，多一個 `id` 不影響使用者能送什麼。

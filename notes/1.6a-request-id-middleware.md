# 1.6A request-id middleware

> tag：無（1.6 拆成 A/B，`step-01-06` 在 1.6B 完成後才打）
> 檔案：`backend/internal/shared/middleware/requestid.go`、`requestid_test.go`、`backend/cmd/api/main.go`、`main_test.go`
> 對應：PRD 3.3「每一行 log 都帶 request-id」的前半：先讓每個請求都**有** id

## 目標與結果

每個回應都帶 `X-Request-Id`；請求帶了合法的 id 就沿用，否則新產生。

- `make test` 通過，新增 `internal/shared/middleware` 套件
- curl 兩次 → 兩個不同的 26 字元 id；`-H 'X-Request-Id: my-trace-1'` → 沿用；`'bad id!'` → 被換掉
- 404 / 405（mux 自己產生的回應）也有 id，因為 middleware 包在 mux 外面

## 學到的概念

### 1. Middleware 與洋蔥模型

middleware ＝「收一個 `http.Handler`、回傳一個包了一層的 `http.Handler`」的函式。
比喻：大樓警衛，進出都經過他。

```go
func Hello(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// before: on the way in
		next.ServeHTTP(w, r)
		// after: on the way out
	})
}
handler := A(B(mux)) // request: A → B → mux → B → A
```

- `http.HandlerFunc(...)` 是**型別轉換**，讓普通函式擁有 `ServeHTTP` 方法
- 跟 Express 的 `app.use((req,res,next)=>…)` 同概念，但 Go 的 `next` 是你手上明確的 handler

### 2. `context.Context`：跟著請求走的資料袋

```go
type ctxKey struct{}                                 // private key type
ctx := context.WithValue(r.Context(), ctxKey{}, id) // new ctx; old one unchanged
next.ServeHTTP(w, r.WithContext(ctx))                // must pass the NEW request down
id, _ := ctx.Value(ctxKey{}).(string)                // two-value assertion: no panic
```

- context 是不可變的：`WithValue` 回傳新的，所以一定要 `r.WithContext(ctx)` 傳下去
- **為什麼要鑰匙**：同一個 context 之後會放很多東西（request-id、登入使用者、逾時），
  存取都要指定「哪一個」，就像 map 的 key
- **為什麼鑰匙是私有型別、不用字串**：字串誰都打得出來，別的套件用同一個字串就會覆蓋；
  Go 比較 key 時連型別一起比，小寫的 `ctxKey` 只有本套件做得出來
- 鑰匙不外流，外部只能透過 `RequestIDFrom(ctx)` 取值

### 3. Header 與 context 是兩條獨立的路

```go
w.Header().Set(HeaderRequestID, id)   // to the client (must be set BEFORE next writes)
r.WithContext(ctx)                    // to inner code (logs in 1.6B)
```

### 4. 不信任使用者給的 header

```go
var validID = regexp.MustCompile(`^[A-Za-z0-9-]{1,64}$`)
```

- 夾換行的 id 寫進 log 會偽造出一行假的 log（log injection）；超長字串也會灌爆 log
- `MustCompile` 放在套件層級：只編譯一次，pattern 寫錯就在啟動時 panic
- `^` `$` 是錨點：沒有它們，`MatchString` 問的是「**有沒有一段**符合」，
  有了才是「**整個字串**都符合」
- 空字串不符合 `{1,64}`，所以「沒帶」和「不合法」走同一條路 → `rand.Text()`
- 用 `crypto/rand`（猜不到），不用 `math/rand`

### 5. Header 名稱不分大小寫

`Header.Get("X-Request-ID")` 和 `Get("X-Request-Id")` 結果一樣：Go 會先轉成 canonical form
（每個單字首字母大寫）。統一用 `middleware.HeaderRequestID` 常數就不必煩惱。

## 學習者的問題

1. **為什麼要 `if !validID.MatchString(id) { id = rand.Text() }`？**
   使用者給的 id 不合格（沒帶、有怪字元、太長）就丟掉換自己的，防 log injection。
2. **`ctxKey` 真正的功能？** 見概念 2：context 是放很多東西的袋子，鑰匙指定拿哪一個；
   私有型別保證不撞號。
3. **`next.ServeHTTP(w, r.WithContext(ctx))` 是傳下去嗎？** 對。忘了 `.WithContext`，
   內層讀到的都是 `""`。
4. **`seen` / `incoming` / `got` 的命名，和兩個 `!=`？**
   `incoming`＝送進來的、`got`＝回應 header 拿到的、`seen`＝內層從 context 看到的。
   `seen != got` 確認 context 和 header 是同一個 id（log 讀 context、使用者看 header）。
   `(got == tt.incoming) != tt.wantSame`：一行同時檢查「該沿用有沿用、該換有換」。
5. **為什麼 `newMux` 改成 `newHandler`？** 包了 middleware 之後回傳的不再是 `*http.ServeMux`，
   而是 `http.Handler`；改名讓名字誠實。測試也因此跑到和正式環境一樣的整條洋蔥。

## 自我檢查

**Q1：把 `next.ServeHTTP(w, r.WithContext(ctx))` 改成 `next.ServeHTTP(w, r)` 會怎樣？**
- curl 仍看得到 `X-Request-Id`：設定 header 的那行只用到 `w`，跟 `r` 無關
- `requestid_test.go` 四個案例都在 `seen != got`（第 40 行）失敗：`got` 有 id、`seen` 是 `""`
- `main_test.go` 不會失敗：它只檢查 header。不同層的測試守不同的東西

**Q2：拿掉 `^` `$` 會怎樣？**
- `"abc\nevil"` 會被接受（裡面有 `abc` 這段符合）
- `(got == tt.incoming) != tt.wantSame` 報錯；「newline」和「too long」兩個案例都失敗
  （65 個 `a` 的前 64 個就符合）
- 1.6B 把 id 寫進 log 時會有 log injection 風險

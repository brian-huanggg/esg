# Redis

## Redis 的抉擇

Redis 的決策有兩層：**資料怎麼和 DB 配合（快取模式）**，以及**部署拓樸**。

### 快取模式

| 模式 | 做法 | 優點 | 風險 | 適用 |
| --- | --- | --- | --- | --- |
| Cache-aside（最常用） | 讀時先查 Redis，沒有就查 DB 再回填；寫時更新 DB 並刪除快取 | 簡單，Redis 掛了還能退回 DB | 短時間可能讀到舊資料；快取同時失效會造成雪崩 | 提案列表、使用者資料 |
| Write-through | 寫入時同步寫快取和 DB | 快取永遠是新的 | 兩次寫入，沒有分散式交易；其中一邊失敗就不一致 | 讀寫都頻繁、且接受複雜度時 |
| Write-behind | 先寫 Redis，之後非同步刷回 DB | 寫入最快 | Redis 掛掉會**遺失資料** | 不適合你的專案（尤其稽核和提案） |
| Redis 當唯一儲存 | 資料只在 Redis | 最快 | 持久性和一致性要自己扛 | 限速、暫時性計數器 |

**對照你的專案：**

- **Session**：cache-aside，TTL 設短。DB 仍是真相來源，登出時要**同時刪除快取**，否則已登出的 Session 還能用。
- **登入限速和鎖定計數**：Redis 當權威，用 `INCR` 加 `EXPIRE` 或滑動視窗。這是最適合 Redis 的場景，因為資料短命且高頻。要先決定 Redis 掛掉時是 fail-open（放行）還是 fail-closed（擋下），這是安全決策，不是技術細節。
- **審計與提案寫入**：絕對不要 write-behind，也不要只寫 Redis。

### 部署拓樸

| 拓樸 | 說明 | 何時選 |
| --- | --- | --- |
| 單點 | 一個實例，搭配 RDB 或 AOF 持久化 | 你的規模。快取遺失只是變慢，不是事故 |
| Replica + Sentinel | 一主多從，Sentinel 偵測故障並自動切換 | 需要高可用，但資料能放進單機記憶體 |
| Cluster | 資料切成 16384 個 hash slot，分散在多個主節點 | **資料量或吞吐量超過單機**時才需要 |

Cluster 常被過度選用。它有實際成本：跨 slot 的多 key 操作和 Lua script 受限（要用 hash tag 把相關 key 放同一 slot），維運也複雜。單機 Redis 輕鬆處理每秒數萬次操作，你的專案很難碰到上限。

另外要知道，Redis 的主從複製是**非同步**的，故障切換時可能丟失最後幾筆已確認的寫入。所以放進去的資料要能接受「偶爾遺失」。

**常見坑**（用了就要處理）：

- 熱門 key 同時過期，大量請求一起打到 DB（cache stampede）：用 singleflight 合併請求，TTL 加隨機抖動。
- Redis 變慢拖垮整個後端：設短 timeout，加熔斷，逾時就退回 DB。

我的建議：**單點加 Sentinel（或託管服務）就夠，Cluster 留到資料量逼你再選。**

## Row lock 的問題，以及真正的壓力在哪

**Row lock 是什麼：** InnoDB 在 `UPDATE` 時會對該列加排他鎖，直到交易 COMMIT 才釋放。

```sql
UPDATE login_attempts SET fail_count = fail_count + 1 WHERE key = 'ip:1.2.3.4';
```

同一列的其他交易必須排隊。鎖本身不是壓力，**等待才是**。熱點列的吞吐量上限約等於 `1 ÷ 鎖持有時間`：鎖持有 10 ms，那一列每秒最多更新約 100 次。在 Galera 上，持有時間還包含認證的網路往返。如果交易裡同時做了別的事（上傳檔案、寫稽核），鎖握得更久。

**那真正的壓力是計數器、註冊，還是查表？** 依我的判斷，排序如下：

| 排名 | 來源 | 為什麼 |
| --- | --- | --- |
| 1 | **Session 驗證與滑動逾時** | 每個請求都要查 Session，是 QPS 最高的查詢。如果每次請求還要更新 `last_active_at` 來實作「閒置 30 分鐘」，就變成**每個請求一次寫入**，而且在 Galera 上每次寫入都要複製 |
| 2 | **提案列表查詢** | 這是 PRD 的效能目標（RPS ≥ 100、p95 < 300 ms）。索引設計和分頁方式決定成敗 |
| 3 | **審計 hash chain** | 防竄改鏈的每筆紀錄都依賴上一筆的雜湊，必須「讀最後一筆、再寫新一筆」。這是**全域序列化點**，而且和業務寫入在同一個 transaction，等於所有寫入排隊過同一個窄門 |
| 4 | **登入失敗計數器** | 平常寫入量很低。但遭受攻擊時，「用 DB 防禦攻擊」的機制會先被攻擊打爆。注意它是每個帳號、每個 IP 各一列，不同使用者之間不互相競爭，問題在攻擊時的寫入量 |
| 5 | **註冊** | 頻率低，`UNIQUE` 索引很便宜。註冊的瓶頸是 bcrypt（cost 10 約 50 到 100 ms 的 CPU），壓力在後端 CPU，不在 DB |

兩個修正方向：

- Session 更新降頻：只在 `last_active_at` 超過 1 分鐘前才更新，寫入量可降 99%，而 30 分鐘逾時的精度幾乎不受影響。
- Hash chain 要想清楚序列化的範圍，例如依資源分鏈，或改成異步批次封鏈（但這會和「沒有稽核就沒有成功寫入」的規則互相拉扯，要明確取捨）。

**最重要的一點：不要憑感覺猜，量測。** 觀察這些東西：慢查詢日誌、`information_schema.INNODB_TRX` 與 `data_lock_waits`、`SHOW ENGINE INNODB STATUS`，以及 Galera 的 `wsrep_local_cert_failures` 和 `wsrep_local_bf_aborts`（認證失敗次數）。

# V1-V4 架構設計

## 先講思考方式：架構是被數字推著走的

資深工程師不會先挑技術，而是先回答五個問題：

1. **誰在用、多少人？**（DAU、尖峰同時在線）
2. **流量長什麼形狀？**（平均 RPS × 尖峰倍率，是持續流量還是截止前爆量）
3. **資料多大、怎麼長？**（筆數、檔案總量、讀寫比）
4. **壞掉的代價是什麼？**（可用性、資料遺失、稽核要求）
5. **現在的瓶頸是哪一個資源？**（CPU、DB 連線、DB 寫入、頻寬、磁碟）

每升一個版本，都要有一個**可量測的觸發條件**。沒有觸發條件就不升級，因為每多一個元件，就多一種故障模式、多一份維運成本。

## 先估算：這個專案的真實規模

假設公司有 2,000 位 IT 員工：

- 提案約 500 份，每份簡報 5 MiB，總檔案量約 2.5 GB。
- 平均 RPS 小於 1。真正的壓力是**截止前一小時爆量**，尖峰倍率可能是平均的 50 到 100 倍，約 20 到 50 RPS。
- PRD 要求 10,000 筆下 RPS ≥ 100、p95 < 300 ms。這遠高於真實需求，是用來逼你做索引與分頁，屬於工程練習。

這個專案的流量其實落在 V1 以下。PRD 選了 Galera、Kubernetes、ArgoCD，是為了學習與合規，不是流量逼出來的。你要能分辨「需求推動的設計」和「學習目的的設計」，這是 principal 的基本功。

## 各版本設計

### V0：單機版（< 100 人，< 1 RPS）

```text
Browser ──> Go binary（含靜態檔）──> MariaDB（單機）
                      └──> 本機磁碟（簡報檔）
```

- 一個 Go 程序，一個資料庫，檔案放本機磁碟。
- 用 `docker compose` 一鍵啟動，備份靠 `mysqldump` 加 rsync。
- 保留的原則：**模組邊界、OpenAPI 先行、資料庫約束、DB 時間當唯一時鐘**。
- 可以省略：MinIO、Vault、K8s。
- **升級觸發**：需要多人同時維運、需要零停機部署，或單機故障無法接受。

### V1：PRD 目前的版本（數千人，10 到 100 RPS）

```text
Browser ─> Ingress ─> Nginx+SPA ─/api─> Backend ×N（無狀態）─> MariaDB Galera
                                                      ├─> MinIO
                                                      └─> Vault
```

- 後端**無狀態**，Session 放資料庫，所以能直接水平擴到 N 個 replica。
- 檔案搬到 MinIO，因為多個 replica 不能共用本機磁碟。
- 用 Galera 取得資料庫高可用。
- 這版最大的價值是**把狀態集中到三個地方**：DB、MinIO、Vault。後面所有擴充都靠這個前提。
- **升級觸發**：以下任一項持續出現。
  - 列表 API p95 > 300 ms，且已加索引、調過連線池。
  - DB CPU 長期 > 60%。
  - Session 查詢佔了 DB 查詢量的一半以上。
  - 下載流量讓 Backend 的網路或記憶體吃緊。

### V2：讀多寫少的優化（數萬人，100 到 1,000 RPS）

先擴「讀」，因為讀通常是寫的 10 倍以上。

```text
Browser ─> CDN（靜態檔）
        └> LB ─> Backend ×N ─> Redis（Session 快取、列表快取、限速計數）
                           ├─> DB Primary（寫）──> Read Replica（讀）
                           └─> MinIO（改用 presigned URL 下載）
                 Worker ×M（孤兒檔清理、Excel 匯出、統計）
```

| 瓶頸 | 做法 | 對應 PRD 的取捨 |
| --- | --- | --- |
| 每個請求都查 Session | Redis 快取，TTL 短，DB 仍是真相來源 | 保留只存 SHA-256 雜湊的原則 |
| 登入限速、鎖定計數打到熱點列 | 計數器改放 Redis | PRD 現在放 DB，量大會產生 row lock 競爭 |
| 列表查詢重 | 讀寫分離、覆蓋索引、keyset 分頁取代 offset | 深分頁 offset 會越翻越慢 |
| 下載占用 Backend | 改用 presigned URL，後端只做授權 | PRD 現在刻意不用；量大後這是最划算的減負 |
| 匯出、統計卡住請求 | 丟給 Worker 非同步處理 | 加分功能自然落在這裡 |

**要特別小心的地方：**

- 讀寫分離有**複製延遲**。使用者剛送出提案，馬上讀列表可能看不到，所以「寫完立刻要讀自己的資料」的路徑要走 Primary。
- 快取一定要想好失效策略，否則會出現授權資料過期。
- **審計必須與寫入同一個 transaction**，這是 PRD 的硬規則，V2 仍然不能破壞它。

**升級觸發**：寫入成為瓶頸（Primary CPU 或 commit 延遲）、單一 DB 的資料量或維運風險過大，或不同模組需要獨立擴展、獨立發布。



### V3：拆分服務（數十萬人，1,000 到 10,000 RPS）

這時才用 modular monolith 預留的「縫」切開。**沿著模組邊界拆，而不是重寫。**

```text
              ┌─> Auth Service ──> Redis / Auth DB
API Gateway ──┼─> Proposal Service ──> Proposal DB（分片）
              ├─> Slides Service ──> 物件儲存 + CDN
              └─> Search Service ──> OpenSearch
         事件匯流排（Kafka / NATS）──> Audit Consumer ──> 只增不改的稽核儲存
```

| PRD 模組 | 拆分理由 |
| --- | --- |
| `auth` | 流量最高、與業務無關、最適合獨立擴展與獨立安全審查 |
| `slides` + `storage` | 吃頻寬與 CPU，擴展特性和其他模組完全不同 |
| `audit` | 寫入量大、只增不改，適合事件串流加列式儲存 |
| `proposal` | 核心業務，最後才動，必要時按 event 或 tenant 分片 |

**代價很具體：**

- 原本一個 transaction 能保證的「沒有稽核就沒有成功寫入」，跨服務之後不再自動成立。需要 **Transactional Outbox**：業務資料與事件在同一個 DB transaction 寫入，再由 relay 發到 Kafka，並接受最終一致與冪等處理。
- 原本一個 JOIN 解決的查詢，變成跨服務呼叫，要處理超時、重試、熔斷。
- 需要分散式追蹤。PRD 的 request-id 在這裡就從「方便除錯」升級成「沒有它就無法除錯」。

**升級觸發**：多團隊協作時互相卡發布，或是要服務多個公司／多個賽事。

### V4：多租戶與多區域（百萬人以上）

- **Cell-based 架構**：把使用者切成獨立的 cell，每個 cell 是完整的一套系統，故障範圍被限制在單一 cell。
- 多區域部署、資料落地合規、全域路由。
- CQRS：寫模型與讀模型分離，讀模型由事件投影出來。

對一個 ESG 競賽平台來說，這一層幾乎永遠用不到，我列出來是讓你看到演化的終點長什麼樣。

## 一張總表

| 版本 | 規模 | 核心手段 | 新增的複雜度 |
| --- | --- | --- | --- |
| V0 | < 100 人 | 單機、模組邊界 | 幾乎沒有 |
| V1 | 數千人 | 無狀態後端、狀態集中 | 多個 replica、Galera 維運 |
| V2 | 數萬人 | 快取、讀寫分離、非同步 Worker | 一致性、快取失效 |
| V3 | 數十萬人 | 沿模組縫拆服務、事件驅動 | 分散式交易、可觀測性 |
| V4 | 百萬人以上 | Cell、多區域 | 全球化維運 |

## 這份 PRD 裡值得你當練習題的觀察

1. **哪些決定在 V1 合理、V3 會變成障礙？** 例如 Session 與限速計數器放 MariaDB、後端串流下載、所有請求都要查 DB 時間。
2. **哪些決定不管多大都該保留？** 資料庫約束優先、雙 ID 策略、先寫 OpenAPI、儲存一致性（新 key 加 `pending_file_deletion`）。這些是讓你日後能無痛演化的基礎。
3. **MariaDB 10.5 已 EOL**，PRD 的待確認事項也提到這點。這個問題和流量無關，屬於安全與維運風險，應該在任何擴容之前先處理。
4. **擴容的第一步永遠是量測。** 在 10,000 筆資料壓測前，先決定要看哪些指標（p95、DB 連線池等待時間、慢查詢）。

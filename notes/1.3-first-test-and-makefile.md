# 1.3 第一個測試與 Makefile

> tag：`step-01-03`　檔案：`backend/cmd/api/main.go`、`backend/cmd/api/main_test.go`、`Makefile`
> 對應：PRD「後端測試覆蓋率 >= 80%」；測試 3.4

## 目標與結果

在專案根目錄執行 `make test`，health handler 的測試通過。執行 `make cover`，印出覆蓋率。

```
$ make test
cd backend && go test ./...
ok  	github.com/brian-huanggg/esg-award-registration/backend/cmd/api	(cached)

$ make cover
cd backend && go test -cover ./...
ok  	github.com/brian-huanggg/esg-award-registration/backend/cmd/api	(cached)	coverage: 54.5% of statements
```

`(cached)` 的意思是程式碼和測試都沒有改，Go 直接沿用上次的結果。想強制重新跑，加上 `-count=1`。

## 學到的概念

### 1. 把 main 縮到最小：main → run → newMux

```go
func main() {
	if err := run(); err != nil {
		log.Fatal(err)
	}
}

func run() error {
	log.Println("listening on :8080")
	return http.ListenAndServe(":8080", newMux())
}

func newMux() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /api/health", handleHealth)
	return mux
}
```

| 函式 | 負責 | 能不能測 |
|---|---|---|
| `newMux()` | 建立路由表並回傳 | ✅ 測試直接呼叫，不用開 port |
| `run()` | 開 port，出錯時回傳 error | 會卡住，所以先不測 |
| `main()` | 呼叫 run，有錯就結束程式 | 不測，只剩 3 行 |

原則：把難測的東西（網路、結束程式）推到最外面，邏輯放在可以直接呼叫的函式裡。

### 2. Mux 是什麼

Mux 是 multiplexer（多工器）的縮寫。它就像公司的總機：伺服器只有一個入口（port 8080），
mux 依照「方法 + 路徑」把每個請求轉接給對應的 handler，找不到就回 404。
Express 叫 `Router`，Spring 叫 `DispatcherServlet`。

### 3. `_test.go`、`httptest`、ServeHTTP、Recorder

- 檔名以 `_test.go` 結尾的檔案只在 `go test` 時編譯。它和 `main.go` 屬於同一個 package，所以可以呼叫小寫開頭的 `newMux()`。
- `ServeHTTP(w, r)` 是真的處理邏輯，不是假的伺服器。正式上線時，`ListenAndServe` 每收到一個請求就呼叫它一次；測試則跳過網路，直接呼叫它。
- `httptest.NewRequest`：造出一個假的請求。第三個參數是 **request body**，health 不需要，所以傳 `nil`。
- `httptest.NewRecorder()`：一台錄音機（黑盒子）。它不會把回應送到網路上，而是記錄下來，讓測試事後檢查 `rec.Code`、`rec.Header()`、`rec.Body`。

```go
req := httptest.NewRequest(http.MethodGet, "/api/health", nil)
rec := httptest.NewRecorder()
newMux().ServeHTTP(rec, req)
// rec.Code == 200, rec.Body.String() == "{\"status\":\"ok\"}\n"
```

### 4. 表格驅動測試（table-driven test）

```go
tests := []struct {      // ① 當場定義型別：一個 slice，元素是匿名 struct
	name       string
	wantStatus int
}{                       // ② 當場填資料
	{"get ok", 200},
	{"post not allowed", 405},
}

for _, tt := range tests {             // _ 丟掉用不到的索引，tt = 這一輪的案例
	t.Run(tt.name, func(t *testing.T) { // 每一列是一個子測試
		// ...
	})
}
```

- `want` 是預期值，`got` 是實際值，這是 Go 的命名慣例。`wantBody` 比對的是 **response body**。
- TypeScript 對照：`const tests: {name: string; wantStatus: number}[] = [...]`，以及 Vitest 的 `it.each`。
- 這一步的三個案例，各守住一個承諾：
  - GET 回 200 加 JSON：正常的行為
  - POST 回 405：路由只接受 GET
  - 不存在的路徑回 404：不會轉接錯路徑

### 5. `*testing.T`

`t` 是測試框架交給你的遙控器：
- `t.Errorf`：記錄失敗，然後繼續往下執行
- `t.Fatalf`：記錄失敗，立刻停止這個測試
- `t.Run`：開一個子測試

參數前面的 `*` 代表指標，也就是拿到框架手上的同一個 `t`，不是一份複本。如果拿到的是複本，標記的失敗框架看不到。
`go test` 只會執行「名稱以 `Test` 開頭、參數是 `*testing.T`」的函式。

### 6. 為什麼要檢查 Content-Type

body 正確，不代表 header 也正確。拿掉 `w.Header().Set("Content-Type", ...)` 那一行，
Go 會自己猜成 `text/plain; charset=utf-8`。這時只看 body 的測試還是會通過，但前端可能就不會把回應當成 JSON 解析。
測試把「Step 1.2 驗收過的事」固定下來，以後被改壞時會馬上失敗。這種測試叫迴歸測試（regression test）。

### 7. 覆蓋率（coverage）

覆蓋率 = 測試時至少被執行過一次的陳述句數 ÷ 全部的陳述句數。這一步是 6 ÷ 11 = 54.5%。

```bash
cd backend && go test -coverprofile=coverage.out ./cmd/api && go tool cover -html=coverage.out; cd ..
# 沒有瀏覽器時改用：go tool cover -func=coverage.out
# coverage.out 已經在 .gitignore 裡
```

覆蓋率是結果，不是目標。拿掉所有檢查、只留下呼叫，覆蓋率一樣是 54.5%，但這樣的測試什麼都沒有驗證。PRD 的門檻是 80%，從 Step 1.9 開始強制。

### 8. Makefile

```make
.PHONY: test cover

test:
	cd backend && go test ./...

cover:
	cd backend && go test -cover ./...
```

- 指令行的開頭一定要是 **Tab**，不能是空白，否則會出現 `missing separator`。
- `.PHONY`：告訴 make，`test` 不是一個檔案。如果專案裡剛好有一個叫 `test` 的檔案，沒寫 `.PHONY` 的話 make 會什麼都不做。
- 每一行指令在各自的 shell 裡執行，所以 `cd` 必須和 `go` 指令寫在同一行，用 `&&` 串起來。
- `./...`：這個資料夾以及底下的所有 package。

### 9. `go test -v`

`-v` 是 verbose（詳細）的意思。它會列出每個測試和子測試的 `=== RUN` 和 `--- PASS`。
`t.Log` 印出的內容，只有在加上 `-v` 或測試失敗時才會顯示。不加 `-v` 時，失敗一樣會印出來，所以 `make test` 不加 `-v`。
提醒：有些工具的 `-v` 代表 version，遇到新工具時先用 `--help` 確認。

## 學習者的提問

1. **Mux 是什麼，為什麼叫 Mux？** 見概念 2。
2. **為什麼要拆成 run 和 newMux？** 見概念 1。
3. **wantStatus 和 wantBody 是預期值嗎？body 是哪一個？** 是預期值。body 指的是 response body，request body 是 `NewRequest` 的第三個參數。
4. **`_, tt` 是什麼？為什麼要用 `*testing.T`？** 見概念 4、5。
5. **`[]struct{}{}` 是什麼意思？** 當場定義一個匿名 struct 的 slice，同時填入資料。見概念 4。
6. **ServeHTTP 是假的 HTTP server 嗎？** 不是，它是真的處理邏輯。假的只有請求和 Recorder。
7. **Recorder 是什麼意思？** 錄音機（黑盒子），把 handler 寫出的回應記錄下來。
8. **為什麼要檢查 Content-Type？** 見概念 6。
9. **覆蓋率怎麼算？為什麼只測這幾個案例？** 見概念 7，以及概念 4 的「三個承諾」。
10. **`go test -v` 的 v 是什麼？** verbose。見概念 9。

## 自我檢查

**Q1：覆蓋率為什麼是 54.5%？哪些程式碼沒有被執行到？為什麼不測它們？**

沒被執行到的 5 條：`main()` 裡的 `if err := run()` 和 `log.Fatal(err)`、`run()` 裡的 `log.Println` 和 `return http.ListenAndServe`，
以及 `handleHealth` 裡錯誤分支的 `log.Printf`。
（一開始以為 `mux := http.NewServeMux()` 也沒被執行到，其實每個子測試都會呼叫 `newMux()`，所以它有被執行。）
不測的原因：`ListenAndServe` 會一直等待請求、不會回來，測試會卡到逾時，而且可能和正在使用的 8080 port 衝突。
`log.Fatal` 會呼叫 `os.Exit(1)`，直接結束整個測試程式。`log.Printf` 只有在寫回應失敗時才會執行，正常的測試走不到。

**Q2：把 `"GET /api/health"` 改成 `"/api/health"`，哪一個案例會失敗？**

POST 那一個。所有方法都會進到 `handleHealth`，所以 POST 收到 200，不是預期的 405：
`main_test.go:30: status = 200, want 405`。GET 和 404 的案例照樣通過。

**Q3（補答 Step 0.2）：把 `.gitignore` 的 `.env.*` 和 `!.env.example` 對調，會怎樣？**

git 以「最後符合的那一條規則」為準。目前 `!.env.example` 在後面，所以 `.env.example` 會被 commit。
對調之後，最後符合的規則變成 `.env.*`，`.env.example` 就被忽略了，協作者拿不到環境變數的範本。
原則：例外規則（`!`）一定要寫在它要排除的規則後面。

**Q4（補答 Step 0.2）：誤 `git add` 的檔案，怎麼移出暫存區而不刪掉檔案？**

`git rm --cached <檔案>`，或是 `git restore --staged <檔案>`。
如果檔案已經被 git 追蹤，`rm --cached` 代表「從 repo 刪除這個檔案」，`restore --staged` 只是取消這次的 add。
所以單純 add 錯檔案時，用 `restore --staged` 比較保險。

## 學到的概念

### 1. 規格先行（spec-first）

順序固定是：**改規格 → 產生程式碼 → 實作**。`api/openapi.yaml` 是前後端共用的藍圖。

```yaml
paths:
  /api/health:
    get:
      operationId: getHealth          # -> Go method name GetHealth
      responses:
        "200":
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Health"
components:
  schemas:
    Health:
      type: object
      required: [status]              # required -> string, not *string
      properties:
        status:
          type: string
          enum: [ok]                  # -> type HealthStatus string; const Ok
```

- `paths`：有哪些網址和方法。`responses`：每個 status code 回什麼。`components/schemas`：可以重複使用的資料形狀。
- `$ref`：參照型錄裡的 schema。好處是可以重複使用、產生的型別有好名字，前端的 TS 型別也會用同一個名字。

### 2. 工具鏈：make → go generate → go tool → oapi-codegen

```
make gen
  → cd backend && go generate ./...
  → 找到 gen.go 的 //go:generate，切換到 internal/shared/api/ 再執行
  → go tool oapi-codegen（版本鎖在 go.mod 的 tool 區塊）
  → 讀 oapi-codegen.yaml + openapi.yaml，寫出 api.gen.go
```

- `go get -tool`：把工具版本記到 `go.mod`，很像 `npm i -D` 加上 `npx`。
- `//go:generate`：`//` 和 `go:generate` 之間不能有空格。
- 設定檔的 `output` 是相對於 `go:generate` 執行的資料夾。
- `api.gen.go` 要 commit，但絕對不要手改，因為下次 `make gen` 會把它整個覆蓋。

### 3. 產生的程式碼要打開來看

- v2.8.2 的 enum 常數叫 `Ok`，不是我們原本以為的 `HealthStatusOk`。名字會衝突時，才會改用比較長的名字。
- v2.8.2 的 strict server 只用標準庫，不需要 `oapi-codegen/runtime`。
- 283 行裡大部分是固定的骨架（參數錯誤型別、路由組裝、strict 轉接）。每多一個 API，大約多 30–50 行。

## 過程中遇到的錯誤

| 現象 | 原因 | 修正 |
|---|---|---|
| `make gen` 沒有輸出，但沒有產生 `api.gen.go` | `gen.go` 只有 `package api`，沒有 `//go:generate` | 補上 directive |
| `field model not found in type codegen.GenerateOptions` | 設定檔把 `models` 打成 `model` | 改成 `models` |
| （還沒觸發）產生的檔名會不對 | `output: api.gengo` 少了一個點 | 改成 `api.gen.go` |

讀 oapi-codegen 的錯誤訊息時，只要看 `new config version` 那一段。`old config version` 那段是它嘗試用舊格式解析失敗，可以忽略。

## 學習者的問題

**Q：`components` → `schemas` → `$ref` 為什麼需要？**
A：像零件型錄加上型錄編號。一個形狀定義一次，到處參照。改欄位只要改一個地方，產生的 Go 和 TS 型別也有清楚的名字（`Health`），不會變成一長串自動取的名字。

**Q：`enum` 是不是像 `[ok, error, ...]`？**
A：對，`enum` 是允許值的清單。改成 `[ok, error]` 就會多一個常數。但存活檢查（liveness）不放 `error`，因為程式掛了根本回不了話。如果要表達「不健康」，要用不同的 status code（例如 503），不是 200 加上 `"error"`。

**Q：跟 Swagger 有關嗎？**
A：有。OpenAPI 的前身就叫 Swagger 規格。Swagger UI 讀的就是這份 `openapi.yaml`。目前 ROADMAP 沒有列 Swagger UI，要加的話之後再討論。想先看效果，可以把 YAML 貼到 editor.swagger.io。

**Q：為什麼幾行 YAML 會產生那麼多程式碼？**
A：大部分是固定的骨架，跟 API 數量無關。它把每個 API 都要重複做的事包了下來，例如參數解析、參數錯誤的回應、`Content-Type`、JSON 編碼和 middleware。

## 自我檢查

**Q1：把 `operationId: getHealth` 改成 `checkHealth` 再跑 `make gen`，會怎樣？**
A：`api.gen.go` 整個重新產生，裡面全部一起改名（`CheckHealth`、`CheckHealthRequestObject`…），所以它自己內部是一致的。對不上的是**手寫**的實作：方法名稱 `GetHealth` 和參數型別 `GetHealthRequestObject`。所以 `go build` 會失敗。這是好事，因為規格和實作不一致，在編譯時就被抓到，不用等到上線才由使用者發現。重構時也不會漏改名字。

**Q2：`gen.go` 是空的，為什麼所有指令都「成功」？怎麼防？**
A：沒有任何工具出錯。`go generate` 找到 0 個 directive，就是沒事可做。空的 package 也可以合法編譯。linter 檢查的是程式碼寫得好不好，不會知道「應該要有某個檔案」。真正的防線有三層：
1. **讓程式碼依賴產生的東西**：1.5 之後 `main.go` 會呼叫 `api.NewStrictHandler`，少了 `api.gen.go` 就會編譯失敗。
2. **驗證預期的產物**：例如 `grep` 確認產生的型別真的存在，不能只看「沒有錯誤訊息」。
3. **CI 檢查**（之後的步驟）：跑 `make gen` 以後，檢查 `git diff` 是不是空的，抓出「改了規格卻忘了重新產生」。

# 5.4 提案 Service + Handler：422 / 409 / 201 + ETag + Location

## 目標與結果

- 新增 `backend/internal/proposal/service.go`：驗證（title 1–100 字、description 最多 2000 字）後呼叫 repository
- 換掉 `handler.go` 的 501 stub：`CreateProposal` 回 201 / 409 / 422，`GetProposal` 回 200 / 404
- `main.go` 手動接線：`NewRepository` → `NewService` → `NewHandler`
- `curl` 驗收：建立回 `201`，帶 `ETag: "1"` 和 `Location: /api/proposals/<uuid>`

`make test` 通過，後端覆蓋率 88.8%。

## 學到的概念

### 1. 三層各回答一個問題

```
請求 → Authenticate（登入了嗎？CSRF 對嗎？）
     → handler（翻譯 HTTP：狀態碼、header）
     → service（輸入合法嗎？）
     → repository（SQL）
```

Spring 類比：`@RestController` / `@Service` / `@Repository`。Go 沒有 DI 容器，
`main.go` 要自己 `NewService(repo)`、`NewHandler(svc, logger)`，這是刻意的明確性。

### 2. 介面放在使用方

```go
type proposalStore interface {
	Create(ctx context.Context, p *Proposal) error
	FindByUUID(ctx context.Context, leaderID int64, id uuid.UUID) (*Proposal, error)
}
```

`*Repository` 不需要 `implements`，方法簽名對得上就自動滿足。測試時手寫 `fakeStore`，不需要 Mockito。

### 3. 錯誤轉狀態碼

| 來源 | 狀態碼 |
|---|---|
| `*ValidationError` | 422 |
| `ErrDuplicateTitle` | 409 |
| `ErrNotFound` | 404 |
| 其他 | 500（只記 log，不洩漏原因） |

### 4. ETag 要帶引號

強驗證器（strong validator）格式是 `"1"`，不是 `1`。之後 5.10 的 `If-Match` 要比對同樣的格式。

### 5. 先 `TrimSpace` 再驗證

沒有 trim，`"   "` 長度 3，會通過「不可為空」並寫入資料庫。

## 問題與解答

**Q：`curl` 回 401，哪裡錯了？**
A：`Cookie` header 要寫 `session=<值>`，`auth.go` 用 `r.Cookie("session")` 依名稱找；
另外 `Content-Type` 要是 `application/json`。

## 自我檢查

1. 別的 Leader 讀你的提案為什麼是 404 不是 403？
   答：`FindByUUID` 的 SQL 同時有 `uuid` 和 `leader_account_id`，查不到就是 `ErrNotFound`，
   handler 分辨不出「不存在」與「不是你的」，也不需要分辨。
2. 拿掉 `strings.TrimSpace(title)`，title 傳三個空白會怎樣？
   答：回 201，資料庫留下只有空白的標題。
